# 变更工单 · 分类浏览「按主题看」+ 主题聚合缓存（R14）

## 1. 为什么

R13 已让 `GET /api/graph/topics` 支持 `category_id`（分类子树 → 条目 → 点），但分类浏览页的呈现模式只有「按集分组 / 平铺」两态，缺入口。开工前先测了代价：

| 探针 | 数字 |
|---|---|
| 「人工智能」子树 | 25 条目 → **4507 点**（全库 4552 点；单条目前 4 大书占 1373 / 820 / 571 / 420 点） |
| `?category_id=…&limit=20`（HTTP，未加缓存） | **6.7–6.9 s**（curl 连测三次稳定）；同参数进程内直调 2.5 s（`_greedy_np` 3.7 s 主导；995 簇 → 合并后 926 主题、落单 1752） |
| 对照：现有「按集分组」`/api/sets/group` | 同分类 **0.27 s**（条目级语义聚类） |
| 对照：`?q=GRPO` | 0.22 s（点域小） |

结论：这个视图的价值在**点级**粒度（条目级已有「按集分组」），但冷启动 3–7 s，做成按钮必须配缓存，否则用户会以为界面卡死。

## 2. 契约变更

| 项 | 变更 | 兼容性 |
|---|---|---|
| `GET /api/graph/topics` | **无**（不加 query 参数，响应 JSON 字段一致） | 纯内部缓存 |
| 响应时效 | 同库、同范围、同参数的结果**最多陈旧 300 s**；数据一变（kpoints 重抽 / ksync --embed）立即换键 | 可观测行为变化，故写本单 |
| `DataLayer.points_fingerprint()` | **新增只读方法**：`点数:最新点时间:向量数:最新向量时间` | 纯新增，无表结构变更 |
| 前端 localStorage | 新增 `knowatlas.catMode`（flat/set/topic）；旧键 `knowatlas.catGrouped` 仍被读取（"0"→flat） | 老用户已有偏好不丢 |
| 表结构 / 字段 / locator scheme / `SOURCE_TYPES` / `STATUSES` / `CONFIG_SCHEMA_KEYS` / 能力注册表 | **无** | canary 六项零漂移 |

## 3. 方案

1. **前端三态**（`web/static/index.html`）
   - `catGrouped`（布尔）→ `catMode`（`flat` / `set` / `topic`）；读取顺序：`knowatlas.catMode` → 旧键 `knowatlas.catGrouped` → 默认 `set`。
   - 统一模式条 `catBarHtml(note)`：三个按钮（📄 平铺 / 📐 按集分组 / 🧠 按主题），当前态加 `.on`；`bindCatBar` 绑定切换并落 localStorage。
   - `renderCategoryView()` 按模式分发：`topic` → `renderCategoryTopics`；`set` 且 >5 条 → `/api/sets/group`（失败/不成组降级平铺）；其余 → `renderCategoryFlat`（复用 `renderEntries(list, prefix)`）。
   - 主题视图：`/api/graph/topics?category_id=<当前分类>&limit=40`，头行「N 条目 → P 点 → M 个主题（共 T 个，取前 M）· 阈值 0.72、合并 0.85、落单 s 点」；每主题 `<details class="topic-row">`（名字 · N 点 · 并 k 簇 · 溯源 x 条目），展开成员点卡，溯源走既有 `openPreview`；加载中提示「大分类首次约 3–7 秒，之后走缓存」。
   - 行渲染与 R13 检索「主题」tab 共用 `topicPointCard` / `topicRowsHtml` / `bindTopicOpen`（防两处漂移）。
   - 主题模式下 `#filter`（来源筛选）**禁用 + tooltip**「主题模式按分类点域聚合，来源筛选不适用」——端点只吃 `category_id`，不静默忽略。
   - 切分类时 `catTopics = null`（服务端缓存兜底重取成本）。
2. **服务端缓存**（`web/api.py`，挂在 `register_routes` 闭包里，随 app 实例生灭）
   - `_TOPICS_TTL = 300.0`、`_TOPICS_MAX = 8`（按写入时间淘汰最旧；单条响应约 140 KB，8 条 ≈ 1.1 MB）。
   - 键 = `库路径 | 点域指纹 | scope(mode,q,category_id) | 点域签名(sha1(排序 point_id)) | limit | merge | merge_threshold`。
     - **点域先算再查缓存**（分类口径实测 53 ms），改分类 / 换检索词直接换键，绝不串味；
     - 指纹覆盖「同数不同内容」的重建，数据写入后无需手工失效。
   - 并发不做 single-flight：多算一次只是慢一点，等锁反而把两类请求串成一队。
3. **明确不做**：不改 `_greedy_np` 归簇算法（会动主题质量，另开工单）；不加 `refresh` 等新参数；不做跨进程/落盘缓存。

## 4. 验证

- 定向回归：`tests/test_web_api.py`（静态页断言）、`tests/test_cloud.py`、`tests/test_timeline.py`、`tests/test_canary.py`。
- 全量 `pytest -q`。
- 真库 curl：`?category_id=…&limit=40` 冷/热两次、`?limit=40` 冷/热两次。

## 6. 风险与回退

- **陈旧窗口**：同数据同范围最多 300 s 旧结果；数据写入即失效，实际风险限于「同一批数据下先改了阈值/命名规则再刷新页面」——重启 serve 即清空。
- **内存**：8 条 × ~140 KB ≈ 1.1 MB 上限，LRU 淘汰，不随分类数量增长。
- **回退**：前端把 `catMode` 置 `flat`/`set` 即绕开主题视图；后端删掉 `_topics_cached` 调用即退回 R13 行为（两处改动互相独立）。
- **已知未解**：首调仍是 3–7 s（算法成本），如需更快得改归簇（`_greedy_np`）或做落盘缓存——留给后续工单。
