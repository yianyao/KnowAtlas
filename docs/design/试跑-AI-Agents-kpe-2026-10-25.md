## 3. 抽样

```
- 评估的对象应当是模型与 Harness 的组合体，而非仅评估模型本身；
  同一模型在不同 Harness 中表现可能差异悬殊。
  > 评估的对象不应只是模型，而应是模型与 Harness 的组合体

- Pass@k 指同一任务运行 k 次只要至少一次通过即算通过，衡量能力上限；
  Pass^k 指同一任务连续运行 k 次要求每次都通过，衡量业务可靠性。
  > 同一任务连续运行 k 次，要求每一次都通过

- 共享上下文的多 Agent 协作中，后续 Agent 接收前一个 Agent 的完整
  对话历史和轨迹……优势是信息不丢失，挑战是上下文可能快速膨胀。
  > 共享上下文意味着后续 Agent 接收前一个 Agent 的完整对话历史和轨迹

- 判断多 Agent 协作是否真正优于单 Agent 的核心判据，是协作过程是否
  引入了单个 Agent 在生成时无法获得的新信息。
  > 核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？
```

## 4. 发现的问题

1. **点数超出 prompt 上限**：要求 1–6 条，实际 5–8 条（均值 5.95），
   模型把 6 当成了下限。需要改成"2–5 条，宁少勿多，没有就返回空"。
2. **PDF 数学/代码符号丢格式**：`Pass@k=1−(1−p)^k` 这类公式渲染成
   `Pass@k=1−(1−𝑝)𝑘`；代码块里的注释会被抽成点（内容对，但不像书的知识）。
   可在 prompt 里要求"代码块只抽其中的工程结论，不抽代码行"。
3. **1 条 quote 未命中**：原文有 ` thinking` 标签，模型改写成了"thinking 标签"；
   已标 `quote_ok=false`，不丢点。
4. **密度偏高**：571 点 / 44 万字 ≈ 每 770 字一个点。是否合适取决于用途；
   要更"少而精"就收紧条数。
