# 变更工单：fetch 候选口径（只取 active + 转正优先）与 `--entry` 定向补抓补抽

- 日期：2026-10-27
- 触发：R16 交接块下一步第 3 条（用户 2026-10-27 21:35 裁决「③a+③b+④ 一起做」）
- 关联：R16（长网页分块）、批次 68（`new_entries=pending` 入库缓冲）、批次 70（条目级形态覆盖 / `purge_entry_points`）

## 1. 现状与问题

### 1.1 `--fetch-limit` 的候选口径错位

`ksync --fetch-limit N` 的 `N` 是**尝试次数**预算（`pipeline/sync.py::_fetch_missing`），
但候选列表来自采集器视图，`[e for e in entries if e.id not in pending_ids]`（sync.py:742）
**不看条目在库里的真实 status**——`entries` 是本次源扫描的全集，`pending` / `rejected` /
`archived` 都在里面，按采集顺序排在前面就会先被尝试。

真库证据（2026-10-27 21:20，只读）：

| 项 | 数 |
|---|---|
| rejected 条目 | 78（其中 22 条**已有正文**，多为 `ebook-treasure-chest · 语言` 系列） |
| pending 条目 | 132（书签待审，未抓正文——抓了也是白花预算） |
| active 条目 | 83 |

用户 19:33 的实测复现（R16 记录）：转正 3 条链接后跑 `--fetch-limit 1`，三条都没被抓，
`fetch_status` 一个都没写——预算被排在前面、早已舍弃的链接吃掉了。

### 1.2 没有「定向」入口

- `pipeline/points.py::run_points_extract(entry_ids=…)` 与 `_candidates(only_ids=…)`
  **早已存在**（批次 70），web 合/拆与 `kpeimport --replace` 都在用；但 CLI 没有暴露。
- `pipeline/sync.py::run_sync(...)` 没有 `entry_ids` 参数：补抓/重分类只能整源全量，
  想补一条要么改代码调内部函数（R16 就是这么干的），要么白跑一轮。

## 2. 方案

### 2.1 fetch 候选口径（无 CLI 签名变化）

`pipeline/sync.py` 新增 `_fetch_candidates(dl, entries, *, entry_ids=None)`：

1. **只取 active**：按库内真实 `status` 过滤（新增 `datalayer/db.py::status_map` 批量读，
   SQL 仍只在 datalayer），`pending`/`rejected`/`archived` 不进候选；
2. **转正优先**：按最近一次转正时间降序排在前面，其余保持采集顺序（稳定排序）；
   转正时间取 `task_log` 既有审计链（`action IN ('bulk_activate','restore')`，
   `target=entry_id`，取 `MAX(at)`）——**不新增 meta 键、不动表结构**；
   `pending→active` 的体检/批量转正走 `bulk_activate`，`rejected→active` 走 `restore`，两者都算；
3. 定向模式（`entry_ids` 非空）不看 status，按用户点名顺序处理。

统计键（只增）：`fetch_candidates`（进候选条数）、`fetch_skipped_non_active`、
`fetch_promoted_first`、`fetch_missing_ids`（定向时源里找不到的 id）。

### 2.2 `--entry` 定向（CLI 签名变化 → 本工单备案）

| 命令 | 参数 | 语义 |
|---|---|---|
| `ksync` | `--entry ENTRY_ID`（可重复） | 只处理这些条目：源扫描后过滤到点名 id（顺序按命令行），**不归档**（定向 ≠ 全量遍历，即使带 `--full` 也跳过 `archive_missing`），默认触发抓正文（受 `--fetch-limit` 上限约束；无该参数时上限=命中条数），抓到后当场重分类 + 判重（沿用既有 `post_fetch`） |
| `kpoints` | `--entry ENTRY_ID`（可重复） | 只抽这些条目：串联既有 `run_points_extract(entry_ids=…)`；沿用批次 70 语义——**跳过游标、会重新调用 LLM**（点 hash 相同只归并溯源，不重复建点），要免费用请先用 `--dry-run` |

`run_sync` 新增关键字参数 `entry_ids: list[str] | None = None`（默认 None = 现状）。

## 3. 影响面

| 项 | 变化 |
|---|---|
| 表结构 / 字段集 / `SOURCE_TYPES` / `STATUSES` | 无 |
| `CONFIG_SCHEMA_KEYS` | 无 |
| locator scheme | 无 |
| 接口签名 | `run_sync(..., entry_ids=None)`；CLI `ksync --entry`、`kpoints --entry`（只增参数） |
| `meta` | 无新增键 |
| 行为口径 | `--fetch-limit N` 的 N 条尝试**只落在 active**；定向模式不归档 |
| 输出 | 新增 4 个统计键（见 §2.1） |

## 4. 验证

1. 单测（新增 `tests/test_entry_targeted.py`）：
   - rejected/pending 条目不占 fetch 预算（`fetch_skipped_non_active` 记账、失败计数不涨）；
   - 刚转正的条目排在候选最前（即使采集顺序在后）；
   - `ksync --entry` 只处理点名条目、不归档未命中条目、源里没有的 id 进 `fetch_missing_ids`；
   - `kpoints --entry` 只抽点名条目；
   - CLI 参数可重复解析。
2. 真库：`ksync --source folders --entry <id> --fetch-limit 1` 与 `kpoints --entry <id> --dry-run` 各跑一次；
3. 全量 `pytest -o addopts= -q`（基线 686 passed / 1 skipped）+ `tests/test_canary.py` 零漂移。

## 5. 风险

| 风险 | 处置 |
|---|---|
| 「转正优先」让老 active 条目永远轮不到 | 只在**有转正记录**的条目上生效；转正集合有限且随预算消耗自然退场 |
| 只取 active 导致 pending 条目永远抓不到正文 | 有意为之（pending=待审，抓正文是白花钱）；转正后立即进候选 |
| `--entry` 跳过游标重复调用 LLM | 沿用批次 70 既有语义并在 help 里写明；点 hash 归并保证不重复建点 |
| 定向模式与 `--full` 组合让人误以为会归档 | 显式跳过并打 `targeted=true` 标记，`--full` 在定向模式下不生效（已在 help 说明） |
