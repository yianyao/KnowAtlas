## 1. 项目定位

**一句话**：不移动、不改写任何原始数据，为分散在各处的个人知识建立一个统一索引层，以分类树 / 词云 / 关系图作为入口，逐层下钻并一键回溯到原始来源。

**大白话类比**：像给全家的藏书建一间"总目录室"——书还在各个房间原地不动，目录室的卡片告诉你每本书放在哪、大概讲什么、和哪些书内容相邻。以后找东西先查卡片，按图索骥，不用翻遍每个房间。

核心特征：

1. 个人使用，单用户；账号密码等凭证一律走配置文件，不硬编码进代码。
2. 顶层工具是编排器：调用各源已有的工具/接口完成导出，不重写每个源的导出逻辑。
3. 分类从大粒度到细粒度逐层归纳，最终落到具体科目级（例："材料入库操作""对话如何描写"）。
4. 点击类别可逐层下钻到具体知识来源条目，条目可跳回原始位置。
5. 统一数据层是唯一事实来源；分类成果可整体导出，不锁死在工具内部。
6. 随时可以把一篇好文章的链接直接发给工具，即刻抓取入树（手动入口，见 §4、§5.1）。

## 3. 关键设计决策

### D1 三层架构 + 两契约

**大白话**：三层 = 翻译官（把各源"方言"翻译成统一结构）、取件员（按地址去把正文取回来）、分析师（看懂内容再归类）；两契约 = 全楼只有一间档案室（所有数据只进那里）+ 一本能力花名册（新增能力只登记，不改大楼结构）。

- **第一层 源适配器（Source Adapter）**：每个知识源一个，职责极窄——读取原始形态，输出统一条目列表。纪律：绝不抓网页、绝不分类、绝不清洗正文，只做"翻译"。
- **第二层 内容获取器（Content Fetcher）**：输入 locator（定位符），输出正文。按 locator 的协议类型注册，不按来源注册——同一个 http 获取器同时服务浏览器收藏夹、微信收藏、腾讯文档链接。新增资源类型 = 注册一个新 handler，已有源自动受益。
- **第三层 语义处理器（Semantic Processor）**：输入"标题 + 正文（可空）"，输出分类路径、标签、摘要。与来源完全无关；LLM 调用只出现在这一层。
- **契约一 统一数据层**：一组 SQLite 表，所有功能只通过这一层读写，是唯一事实来源（见 §5.2）。
- **契约二 能力注册表**：Locator Handler 注册表（协议 → 取件 handler）与 Semantic Task 注册表（任务名 → 处理器）。每个能力有名字、输入契约、输出契约（见 §5.3）。

**理由**：典型反例——GitHub 书签要"知道说了啥"，拆开是两件事：取内容（抓 URL 提取正文）和懂内容（判断语义）。若两者都写进书签适配器，邮件适配器就要重写一遍。功能多的风险不在数量，在挂错层级。

**代价与缓解**：初期多两层间接，感觉"绕"。缓解：注册表保证新增源/新功能始终是"一个新文件 + 一条注册"，不动主流程。

### D2 按源建薄适配器 + 先验结构信号优先，LLM 只做归一与兜底

**不为每层粒度开发独立工具**——若按"粗分类一类工具、细分类一类工具"的方式建，维护成本会急剧膨胀。正确做法是两件事分开：按**源**建薄适配器（一次性翻译，本来就要有），按**任务**建语义处理器（与源无关）。

标题是最廉价、最可靠的粗粒度分类信号，但不够。系统性地使用**先验结构信号**（本项目自定义术语，指知识源自带的、无需推断的结构信息，包括：浏览器收藏夹的文件夹层级、邮件的邮箱文件夹、万兴脑图的节点树、文件系统目录路径、数据库的表名/列名）——这些信号免费、确定、可解释，比 LLM 更可靠。

LLM 只做三件事：把各源先验归一到统一分类体系；对无先验且标题含糊的条目兜底；应用户主动请求的细分。先聚类再让 LLM 为簇命名，比逐条分类更高效。

### D3 分类存储为 DAG（多父），UI 默认呈现为树

"对话如何描写"该挂在「文学创作」还是「AI 工具/提示词」下——这类归属两难在实践中必然大量出现。存储上分类表通过 junction 表支持多父（DAG，有向无环图，指一个节点可有多个父节点的图结构）；展示时按根展开为树，用户无感知。避免"先单继承、后期再迁多父"的数据迁移代价。

### D4 LLM 三级流水线：规则 → embedding → LLM，可插拔、可全离线

分类不直接调 LLM，走三级：规则（关键词/正则/先验映射）→ embedding 聚类（先聚类后命名）→ LLM 批量兜底。任一级可单独关闭或降级；LLM 走 OpenAI 兼容接口，**默认云端 API**（2026-10-19 第二次定稿），保留配置项一键切换本地 Ollama/vLLM（数据不出本机）——只是 base_url + model + api_key 三个配置项，代码不重。

### D5 防腐化纪律

任何功能（含未来新增）只许走"适配器产出 → 数据层 → 功能读取"路径，不允许直接访问原始数据源或自建数据存储。即使"直接读书签 JSON 更快"也要拦下——一旦开先例，增量同步、去重、操作日志全部失效。

| IMA 知识库 | 高 | 官方三条通道：OpenAPI（Client ID + API Key 静态凭证，适合常驻脚本，含 list_notes / list_notebooks / get_note_content 等）；MCP（ima.qq.com/mcp）；网页 cookie 兜底 | 笔记本结构 | P2 |

| 微信收藏 | 中（新路线） | **链接 → 博主名下文章全扒**（2026-10-19 用户定稿）：只取收藏的标题 + URL（favorite.db 轻量提取或手动粘贴均可，不解全文）→ 解析 `__biz` → 用 wechat-article-exporter（开源，MIT）按 biz 拉取该博主全部文章，Markdown 入 content store。原 SQLCipher 全量解密路线保留为可选，不再作为主路线 | 无（链接即先验） | P2 |
| 数据文件（sqlite / PostgreSQL） | 中 | sqlite：schema 自省 + 采样行；PostgreSQL：连接串走配置，psycopg 连接后同样 schema 自省 + 采样行生成条目摘要 | 表名、列名、注释 | P3 |
| 聊天工具（微信） | 中 | 微信聊天记录：集成 WeChatMsg / MemoTrace 系活跃 fork（解密 + 导出 HTML/MD/sqlite），主工具按文件源扫描产物目录 | 会话名、时间 | P3 |

说明一：腾讯文档与 IMA 的官方接口均在 2026-10-19 检索确认存在（docs.qq.com/openapi；ima.qq.com/openapi），与早期"无官方全量导出"的判断不同，接入方案相应上调。

说明二：微信收藏路线经第二次确认改为"链接 → 博主名下文章全扒"（用户决策）：一条收藏链接展开为一个博主的知识切片，顺带解决"只有链接没有内容"的老问题。数据模型上，收藏条目为**种子条目**，扒下的文章为**关联条目**（meta 记 `seed_entry_id` + `biz`），视图上支持"展开该博主全部相关文章"。

说明三：手动链接入口不新增层、不新增 scheme——用户粘贴 URL 等于一个极简源适配器产出 https 条目，之后与书签条目走完全相同的抓取 → 归类链路（见 §5.1）。

说明四：B站收藏夹是第一个“cookie 型凭证”源，以此确立凭证纪律模板：**所有需要账号、密码、cookie、token 的知识源，凭证一律只写入配置文件指向的环境变量（如 `KNOWATLAS_BILI_SESSDATA`），禁硬编码、禁入仓库、禁入日志**；SESSDATA 获取方式（浏览器 F12 → 应用 → Cookies）写入 SOP 故障表。该纪律对后续 IMA、腾讯文档、PostgreSQL、微信等全部凭证型源生效。

## 5. 总体架构与两契约

### 5.1 分层与数据流

```
[各知识源] ──► 源适配器(每源一个, 只翻译) ──► 统一数据层 SQLite（唯一事实来源）
                                                  │
内容获取器(按 locator 协议注册, 跨源共享) ◄────────┤（按需拉取正文）
      └─► content_store（按内容 hash 缓存, 同一内容只存一份）
                                                  │
语义处理器(按 task 注册, 与源无关) ◄──────────────┘
      └─► 分类/标签/摘要写回数据层
                                                  │
视图层（分类树 / 词云 / 关系图 / 时间线）◄─────────┘（只读数据层, 不碰原始源）
```

手动链接提交（kadd / bookmarklet）走的就是这条主线：粘贴 URL → 建条目（入"未分类"暂存区）→ http 获取器抓正文 → 语义分类 → 出现在分类树对应分支。已收藏过的 URL（canonical 规范化后命中）自动合并，不重复建条目。

### 5.2 契约一：统一数据层

#### 统一条目字段

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| id | TEXT | 是 | 稳定 ID：sha1(source_type + 源内唯一键) 前 16 位；重复导入不变 |
| source_type | TEXT | 是 | 枚举：bookmark / folder / emmx / mail / ima / txdoc / db / session / wxfav / manual / wxchat / wxarticle / bili |
| title | TEXT | 是 | 可为空串；UI 回退显示 locator 末段 |
| locator | TEXT | 是 | 符合 §5.4 scheme 规范 |
| native_path | TEXT | 否 | 源自带路径（书签文件夹/邮件文件夹/脑图节点/目录），先验信号 |
| inline_content | TEXT | 否 | 轻量正文片段；大内容入 content_store |
| content_hash | TEXT | 否 | 正文规范化（统一 LF、去首尾空白）后 sha1 |
| meta | TEXT | 是 | JSON 对象，默认 {}；存源特定元数据（发件人、域名、schema、seed_entry_id 等；seed_entry_id 用于公众号扒取文章回溯到触发它的收藏种子条目） |
| created_at | TEXT | 否 | 内容创建时间，ISO 8601；无法解析则 NULL，不臆造 |
| exported_at | TEXT | 是 | 导入时间，ISO 8601 |
| status | TEXT | 是 | active / archived / deleted，默认 active |

#### SQLite 表结构（DDL 草案）

```sql
-- 条目主表
CREATE TABLE entries (
    id             TEXT PRIMARY KEY,
    source_type    TEXT NOT NULL,
    title          TEXT NOT NULL,
    locator        TEXT NOT NULL,
    native_path    TEXT,
    inline_content TEXT,
    content_hash   TEXT,
    meta           TEXT NOT NULL DEFAULT '{}',
    created_at     TEXT,
    exported_at    TEXT NOT NULL,
    status         TEXT NOT NULL DEFAULT 'active'
);

-- 分类表（多父 junction 单独建表，存储为 DAG）
CREATE TABLE categories (
    id         TEXT PRIMARY KEY,
    name       TEXT NOT NULL,
    path       TEXT NOT NULL,          -- 规范化路径，如 "软件/ERP/仓存管理"
    note       TEXT,
    origin     TEXT NOT NULL,          -- prior / rule / embedding / llm / manual
    created_at TEXT NOT NULL
);

CREATE TABLE category_parents (        -- 一个分类可有多个父分类
    category_id TEXT NOT NULL REFERENCES categories(id),
    parent_id   TEXT NOT NULL REFERENCES categories(id),
    PRIMARY KEY (category_id, parent_id)
);

-- 条目-分类多对多（一条内容可挂多个分类）
CREATE TABLE entry_categories (
    entry_id    TEXT NOT NULL REFERENCES entries(id),
    category_id TEXT NOT NULL REFERENCES categories(id),
    confidence  REAL NOT NULL DEFAULT 1.0,   -- 先验映射 1.0；LLM 兜底按输出
    origin      TEXT NOT NULL,               -- prior / rule / embedding / llm / manual
    task_run_id TEXT,                        -- 哪次语义任务写入，可回溯
    PRIMARY KEY (entry_id, category_id)
);

-- 内容缓存（fetcher 产出按 hash 落这里，同一内容只存一份）
CREATE TABLE content_store (
    content_hash TEXT PRIMARY KEY,
    text         TEXT NOT NULL,
    fetched_at   TEXT NOT NULL,
    fetcher      TEXT NOT NULL          -- 哪个 handler 抓的
);

-- 操作日志（分类成果的审计与增量处理基础）
CREATE TABLE task_log (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    at        TEXT NOT NULL,
    task_name TEXT NOT NULL,            -- 能力名或 manual
    action    TEXT NOT NULL,            -- classify / retag / merge / move / archive
    target    TEXT NOT NULL,            -- entry_id 或 category_id
    detail    TEXT NOT NULL DEFAULT '{}' -- JSON：前后值、输入摘要
);

-- 全文检索（中文：trigram 分词开箱可用；关键词统计另配 jieba）
CREATE VIRTUAL TABLE entries_fts USING fts5(
    title, native_path, inline_content,
    content = 'entries',
    tokenize = 'trigram'
);
```

### 5.3 契约二：能力注册表

| 注册表 | 键 | 值 | 说明 |
|---|---|---|---|
| Locator Handler | locator scheme（如 https） | handler 函数 | 输入 locator，输出正文文本；同一 handler 被所有源共享 |
| Semantic Task | task_name（如 classify_coarse） | processor 函数 | 输入"标题 + 正文（可空）"，输出分类路径、标签、摘要 |

能力描述格式（每个能力登记时必须带）：

```
name:            能力名（注册表键）
input_contract:  输入字段与约束
output_contract: 输出字段与约束
version:         语义化版本；输出结构变更必须升版
```

未来功能与系统的交互只有四种：读统一数据、调已有能力、写回统一数据、组合以上三步。四种交互均有稳定接口，任何新想法都只是"新组合脚本"。

### 5.4 locator scheme 命名规范

| scheme | 含义 | 默认 handler |
|---|---|---|
| http:// / https:// | 网页（含 kadd 手动粘贴、书签、邮件内链接） | http_fetcher（含 GitHub 等特化分支） |
| file:// | 本地文件（按扩展名分流 PDF/Office/其他） | file_reader |
| mail:// | 邮件（maildir 路径 + message id） | mail_reader |
| ima:// | IMA 笔记/知识库条目 | ima_client |
| txdoc:// | 腾讯文档 | txdoc_client |
| emmx:// | 脑图节点（文件路径 + 节点 id） | emmx_reader |
| db:// | 数据文件表（sqlite 文件路径 + 表名；PostgreSQL 为 连接串名 + 表名） | db_introspect |
| session:// | AI 会话（映射 session-harvester 输出） | session_reader |
| wxfav:// | 微信收藏（链接路线：收藏条目本身即种子条目；mp.weixin.qq.com 链接直接按 https 处理，扒取的文章落本地文件后按 file:// 处理） | wxfav_reader / https |
| bili:// | B站收藏条目（bvid/avid；视频页 URL、UP主、收藏时间、全部收藏夹 id 入 meta） | bili_reader |

规则：scheme 小写；scheme 表示"按什么协议取内容"，不表示来源类型（来源在 source_type）；file:// 不携带用户特定绝对路径——配置文件里的根目录 + 相对路径拼接，保证换机可迁移。

## 6. 分类体系设计

### 6.1 顶层大类草案（10 类）

1. 文学创作（细分示例：对话描写、人物塑造、情节结构、诗词格律）
2. 软件与 ERP（细分示例：材料入库操作、库存盘点、单据流程）
3. 技术开发（前端 / 后端 / 工具链 / 具体库）
4. AI 工具与提示词
5. 办公与文档（Office / WPS / 腾讯文档技巧）
6. 数据与分析（SQL / Python / 可视化）
7. 学习与教育（课程 / 语言 / 考试）
8. 项目与协作（项目管理 / 团队 / 沟通）
9. 生活与其他（健康 / 理财 / 旅行）
10. 参考与工具书（手册 / 规范 / 速查）

外加"未分类"暂存区（是状态，不是大类）：先验与规则都判不了的条目进暂存区，等人或 LLM 处理，不硬猜。kadd 手动粘贴的链接首站即暂存区，抓取归类后自动迁出。

### 6.2 归纳机制（四步，从便宜到贵）

1. **先验映射**：native_path / 邮箱文件夹 / 脑图节点路径按映射表直接落到分类分支（confidence 记 1.0，origin 记 prior）。
2. **规则**：关键词 / 正则 / 域名规则补第一层没覆盖的。
3. **embedding 聚类 + LLM 命名**：剩余条目向量化，聚类后让 LLM 为簇命名，生成候选子分类，人工确认后生效。
4. **人工校正回路**：分类树上直接改类、合并、移动、多父挂接；全部进 task_log。校正数据同时是 few-shot 与规则学习来源。

细分深度目标：到科目级（"材料入库操作""对话如何描写"）。细分由用户主动请求触发，不默认无限细分。

## 7. 三大视图与下钻交互

| 视图 | 内容 | 交互 |
|---|---|---|
| 分类树（默认，唯一层级导航） | DAG 按根展开为树；节点显示条目数 | 点击类别 → 右侧条目列表（可按 source_type 筛选）→ 双击条目跳转原始 locator；在条目列表选中内容 → 分类树高亮其所在位置（双向联动）；面包屑导航；未分类暂存区常驻 |
| 词云（焦点范围画像 + facet 过滤，**不做层级下钻**） | 生成范围 = 当前选中分类子树（全库→大类→细类→科目），每级词云由该范围条目的标题 + 正文 tf-idf（jieba）生成，字号 ∝ √权重 | 双态词元：**分类词元**（当前范围的子分类名，描边标识）点击 = 进入该分类、分类树同步高亮联动；**内容词元**（关键词）点击 = facet 过滤当前范围（多选 AND），不下钻。词元按主导顶层分类着色，hover 显示跨类分布条形图 |
| 关系图 | 节点为分类或条目；边为共现（多标签共现）、同源、父子；力导布局 | 两种模式：**全库模式**（边粗细 = 共现次数，点击跳转对应分类或条目）；**focus 模式**（点击词元或分类 → 中心为焦点节点，卫星为匹配条目按 source_type 聚合的源节点，大小 ∝ 条目数；二级点击才展开具体条目 top N + "查看全部"；聚焦时非焦点节点置灰） |
| 时间线（延伸） | 按 created_at 分布 | 看知识积累与兴趣迁移；支撑陈旧分支提醒 |

**三视图职责边界**（防止两个视图抢同一职责）：分类树回答"在哪"（层级），词云回答"讲什么"（画像与过滤），关系图回答"和什么相邻"（关联）。

词云不承担层级下钻，原因有二：其一，**词是多归属的、层级是单路径的**——"Python"同时属于「技术开发」和「数据与分析」，点击它"下钻"到哪里语义不成立；多归属用 facet 过滤表达才准确。其二，实证研究表明词云在概览与主题识别任务上表现优、在精确查找任务上 consistently 被用户绕过（Lohmann 等对标签云的综述；Cardew-Hall et al., 2008 发现在具体信息查找任务中用户一致选择搜索界面而非词云）。层级下钻只发生在语义干净的地方：分类词元与分类树。

常显全部射线 = 词数 × 条目数的边量爆炸，是视觉灾难；射线只在 focus 模式展开，且目标按源聚合（边量从词×条目降为词×源，约 10×10 可控）。

## 9. 实现方式与技术栈

### 9.1 实现方式判断

**纯代码编排 + LLM 作为可插拔语义引擎。不需要做成 SKILL。**

- 纯代码负责：配置管理、调用 IMAP 同步工具、读书签 JSON、遍历文件夹、解析 .emmx、调 IMA/腾讯文档 OpenAPI、写 SQLite、分类树 UI、增量同步、检索。
- LLM 负责：先验归一、低置信度兜底、用户请求的细分、聚类命名。默认走云端 API（配置可切本地，见 D4）；凭证走环境变量——若 LLM 与 DeepSeek Fetch 同用 DeepSeek，可共用同一 API key。
- 不做 SKILL 的理由：SKILL 适合"按需调用一次就结束"的能力包；本项目是持续运行、有状态（增量同步、分类树持久化）、有 UI 的个人工具，形态是本地服务 + 可选 LLM 模块，更可控、更易调试。后续可暴露 MCP 只读端点供 agent 查询，那是消费方式，不是项目形态。
- LLM 使用节奏：先人工确认 50-100 条分类结果 → 固化为 few-shot 示例 + 回归测试集 → 再批量跑。分类器每次改版跑回归，防止"修一类坏两类"。

### 9.2 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 语言/运行时 | Python 3.13（venv 隔离） | PDF/Office 解析、SQLite、embedding 生态最全 |
| 服务框架 | FastAPI（绑定 127.0.0.1） | 单用户本地服务，轻量 |
| 数据层 | SQLite + FTS5 | 零运维；trigram 支持中文检索；单文件易备份 |
| 中文分词 | jieba | 词云与关键词统计 |
| 向量 | 本地 embedding（bge-m3 类中文模型，可选依赖） | 语义检索与聚类；装不装都不影响主链路 |
| LLM 客户端 | OpenAI 兼容接口（默认云端，配置可切本地 Ollama/vLLM） | 一套代码两种部署 |
| 网页正文（默认） | httpx + readability-lxml | 零成本，覆盖大多数文章页 |
| 网页正文（可靠兜底） | DeepSeek Fetch API（可插拔后端） | 正文提取质量高；5 元/千次成功请求，个人量级成本可忽略；默认 simple，超时/正文过短自动升级；hash 缓存保证同一 URL 不重复计费 |
| PDF/Office 解析 | markitdown（微软，MIT） | 统一转 Markdown；pdfplumber 兜底 |

| 脑图解析 | 标准库 zipfile + ElementTree | .emmx 即 ZIP + XML，无额外依赖 |

### 10.2 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 微信收藏（新路线）依赖 exporter 登录态与防盗链 | 扒取中断或频率受限 | 独立脚本隔离；登录态失效有明确报错；只扒自己收藏涉及的博主并控制频率；收藏条目本身不依赖 favorite.db 全量解密，始终可用 |
| wechat-article-exporter 项目活跃度 | 公众号扒取中断 | 隔离为独立脚本，失效不拖垮主流程；必要时回退"手动导出 HTML 后按文件源扫描" |
| 微信聊天记录工具 fork 停更 | 解密失效 | 选活跃 fork；失效只损失该源；产物落固定目录的契约不变 |
| DeepSeek Fetch 限流（账号级 5 QPS + 域名级） | 抓取失败 | 429 指数退避；已抓内容按 hash 缓存不重复计费；持续失败自动降级 simple 后端 |
| 腾讯文档 doc/slide 仅导出 PDF | 正文保真度损失 | 二次解析 + 标题级兜底；表格类原生导出不受影响 |
| 腾讯文档 / IMA 接口变更或限流 | 同步失败 | 适配器隔离 + 429 队列降速 + token 过期明确报错（见 SOP 故障表） |
| .emmx 节点在 page.bin 二进制中 | 解析深度受限 | 先用真实文件验证；失败降级标题级，结构信号损失但可用 |
| B站 SESSDATA 过期（有效期约 30 天） | 收藏夹同步失败 | AuthExpiredError 明确报错 + SOP 故障表含 F12 重取步骤；旧条目保留不误删 |
| B站给 fav 接口增补 WBI 签名或触发 412 风控 | 适配器失效 | WBI 签名模块内置可开关（参照 bili-sync）；UA + Referer + ≤2 QPS 降速；失效只损失一个源 |
| 凭证泄露 | 账号风险 | 凭证只进 config/ 且入 .gitignore；配置示例用占位符 |
| 本地 Web 服务暴露面（CSRF / DNS rebinding） | 浏览器内其他网页可往库灌条目、触发抓取计费 | 仅绑 127.0.0.1 不够：Host/Origin 校验 + 写操作本地 token + content-type 白名单（完整方案 §8 五条） |

### 10.3 合规边界

只自动化操作自己账号下有权限的内容（能在浏览器正常打开、能正常导出的，才可用接口批量操作）；企业微信会话存档需管理员授权；微信相关脚本仅用于导出个人数据，注意账号安全，不高频操作；公众号扒取仅限自己收藏涉及的博主，控制频率，不做全网爬取；B站只读自己的收藏夹元数据（标题/简介/链接），不下载视频本体，请求频率 ≤2 QPS。
