# 变更工单 · 点级老化两型（P2）

## 1. 为什么

现状老化是**被动**的：L1 日期规则先标条目 suspect，L2 `aging_judge` 复核条目，
点级老化（批次 93）也只吃「溯源条目已被标 suspect/stale」的点。结果是技术栈层面的
过时（Python 2.7 教程、jQuery 1.x 插件写法）**没人主动发现**——它既不写在日期里，
也不会自动变成 suspect。

P2 要的是主动扫描：按 `kind=hard` 分技术栈批量判「这套技术/这个版本是否已退出历史舞台」，
结论落点级，`stale` 沿用现成机制退出消费面。**只标不删**（删除仍只走 30 天冷却的人裁出口）。

## 2. 契约变更

| 项 | 变更 | 说明 |
|---|---|---|
| `points.meta` | **新增 1 组键** `lifecycle = {kind, verdict, tech, version, evidence, at, model, stage}` | 不改表结构；`kind ∈ {version, retired}`；`verdict ∈ {stale, ok, suspect, keep}`；`at` 是幂等游标（有 `at` 即视为已判） |
| `points.aging_flag` | **stale 复用**（不新增列） | 判定 stale 时调既有 `set_point_aging(pid,'stale',reason)`：退出消费面 + `aging_checked_at` 记游标；`ok`/`suspect`/`keep` **不动 aging 列**（留给 L2 与人裁） |
| 能力注册表 | **新增 `point_lifecycle@1.0.0`** | 登记在 `registry/builtins.py`；因此 canary 的 `capabilities` 指纹**必须更新**（其余五项不变） |
| CLI `kaging` | **新增开关** `--lifecycle` | 与 `--points`/`--sweep` 互斥（退出码 2）；`--limit` 默认 `None`（全库） |
| 数据文件 | 新增 `src/knowatlas/semantic/eol.py`（内置表）+ 可选 `data/eol.json`（覆盖/扩充） | **不是配置键**（不进 `CONFIG_SCHEMA_KEYS`）；`data/` 在 gitignore 内，换机不丢内置表 |
| 表结构 / `SOURCE_TYPES` / `STATUSES` / locator scheme / `CONFIG_SCHEMA_KEYS` | **无** | canary 前五项指纹不变 |

## 3. 实现

### 3.1 `semantic/eol.py`（新增，确定性）

- `EOL`：`{tech: {version: eol_date}}`，只收录**有官方支持矩阵**的技术（python / django /
  nodejs / jquery / vue / angularjs / php / ruby），每项带官方 URL（`SOURCES`）。
- `TECH_ALIASES`：`{tech: (别名…)}`；别名按词边界匹配，**不收录裸 `node`**（会被「节点」误伤）。
- `detect_versions(text)`：抽出 `(tech, 版本)`；支持 `2.7`、`3.x`（家族）、`v3.8`。
- `eol_status(tech, version, today)`：`eol`（日期已过）/ `supported`（未到期）/ `unknown`（表里没有）；
  家族 `N.x` 只在**该大版本全部小版本都 EOL** 时算 `eol`。
- `load_table(data_dir)`：内置表 +（存在时）`data/eol.json` 覆盖合并。

### 3.2 `semantic/tasks/point_lifecycle.py`（新增，退场型 LLM）

输入是**去重后的技术名列表**（按技术栈分组，而不是逐点），输出 `{tech: {verdict, evidence}}`：
- `retired`：该技术已停止维护/被官方弃用，**必须**附官方公告 URL 或版本日期；给不出 → `keep`；
- `active`：仍在维护；
- `keep`：判不了。

### 3.3 `pipeline/lifecycle.py`（新增）

`run_lifecycle(cfg, dl, *, limit=0, dry_run=False, llm=None)`：

1. 候选 = `dl.points_of_kind("hard")`（**复用 P0 领域闸门入口**，不另写 SQL）过滤掉
   已有 `meta.lifecycle.at` 与 `aging_flag='stale'` 的点——幂等游标与已退出面双保险；
2. **A 版本型**（零 LLM）：`detect_versions` 命中 EOL → `stale`；命中且全部在支持期 → `ok`；
   命中但版本不在表内 → `suspect`；无版本命中的点留到 B；
3. **B 退场型**（LLM，按技术栈分组）：把剩余点里出现的技术名去重，20 组/批送
   `point_lifecycle`；`retired` → 该技术下所有点 `stale`；`active` → `ok`；`keep` → `keep`；
4. 结论落 `merge_meta_of_point({"lifecycle": {...}})`（**读-改-写整块**，浅合并坑同 P1b）；
   `stale` 追加 `set_point_aging(pid,'stale',reason)`；`log_task(..., "point_lifecycle", ...)` 留痕；
5. LLM 不可用 → A 段照跑，B 段 `llm_skipped`，**不写半成品**。

### 3.4 `cli.py`

`kaging --lifecycle [--limit N] [--dry-run]`；与 `--points`/`--sweep` 互斥（退出码 2）。
报告打印 `version_stale/version_ok/version_suspect/retired_*` 分布与队列提示。

## 4. 验证

```powershell
uv run python -m pytest -o addopts="" -q                       # 全绿（新增 tests/test_lifecycle.py）
uv run python -m pytest tests/test_canary.py -q                # capabilities 更新后零漂移
uv run python -m knowatlas kaging --lifecycle --dry-run        # 只报告不写库
uv run python -m knowatlas kaging --lifecycle                  # 落库；再跑一次零写入（幂等）
```

验收样本（单测内造 6 条）：Python 2.7 教程 → stale；jQuery 1.x 插件 → stale；
Python 3.12 教程 → ok（非 stale）；通用方法论 → 不判；观点文（`kind=opinion`）→ 闸门挡掉；
未来预测（无版本）→ 不判 stale。

## 5. 回滚

```sql
-- 撤销全部点级生命周期结论
UPDATE points SET meta = json_remove(meta, '$.lifecycle');
-- 被本机制判 stale 的点恢复消费面（若还需撤销 aging 结论）
UPDATE points SET aging_flag='', aging_reason='', aging_checked_at=''
 WHERE aging_reason LIKE '%lifecycle%';
```

实跑前备份 `data/knowledge.db` → `temp/knowledge.pre-lifecycle.db`；命令可反复重跑。

## 6. 实跑记录（2026-10-26 00:4x）

| 项 | 结果 |
|---|---|
| 测试 | `pytest -o addopts="" -q` → **611 passed / 1 skipped**；canary 仅 `capabilities` → `e293e25d725c` |
| 备份 | `temp/knowledge.pre-lifecycle.db`（120.6 MB） |
| 真库 A 段（版本型） | 1,579 hard 点 → `version_ok` 2（Vue 3 / Python 3），**`version_stale` 0** |
| 真库 B 段（退场型） | 4 个技术栈（python 29 / nodejs 6 / vue 3 / django 1）→ **37 ok / 0 retired**，1 次 LLM 调用 |
| 幂等 | 重跑 candidates 1,540（无技术栈提及的点，纯正则重扫，零费用）、**零写入零调用** |

**本库 0 stale 是正确结果**：探针确认库里没有「用过时版本」的知识点（无 AngularJS /
jQuery 1.x / Python 2 / TensorFlow 1 等），出现版本的绝大多数是「需要 X 或更高版本」的
环境门槛（已被语境过滤排除）与现行技术（Vue 3、Python 3、Node 22）。

自检抓到的两类假阳性（已修并固化为单测）：

1. `Python 3.x` 被 3.6–3.9 的 EOL 记录带成 stale → 新增 `LIVE_MAJORS`（声明仍有活着的
   小版本的大版本）；
2. `需要 Python 3.10 或更高版本` 被当成「在用 3.10」→ 新增最低版本语境过滤
   （`或更高/及以上/N+`）；顺带修 `Python 2019` 的年份误匹配（`(?!\d)`）。

扩容路径：换来源后若要覆盖更多技术，在 `semantic/eol.py` 的 `EOL`/`SOURCES`/`LIVE_MAJORS`
加一条，或在 `data/eol.json` 里追加覆盖项——**不需要改代码**（`load_table` 会合并）。
