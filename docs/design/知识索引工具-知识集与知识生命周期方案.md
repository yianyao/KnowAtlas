## 2. 用户理念原文

能聚能散能溯源：

0. 知识本身不拘泥于具体载体，而是散落的繁星；
1. 入库最小单位应该是知识点而非某篇文章——由点而成文章，小类归为块，大类成簇，然后是集，最后归大类；
2. 知识点应能溯源到文章（或邮件、记录）本身；分层方法应内聚（树列表只显示大类）；
3. 查询时应视关键词精确度，返回点、块、簇、集、类；
4. 关系图粒度应从大类逐层下钻（技术开发 → 信息安全/后端/系统工具/数据库/前端 → javascript/typescript/css → …），且树节点以自行聚合为主。

能老化：

1. 自动发现过时（技术类，如 basic、python2.0）并自动老化；
2. 代码不能确认的交 LLM；
3. LLM 不能确认的交人裁决；
4. 人裁决之后废弃删除。

能勘误：同一逻辑（代码自动查错 → 改正或老化 → LLM → 人裁决 → 裁决后废弃删除）。

布局反馈（截图）：右边列表不应按文章/网页/邮件等载体形式组织，而应是知识集；知识图/串联/词云/时间线应考虑页签化；数据管理应独立；收藏小书签的用途要说明；总体布局界弄好看，先给图看效果。

## 4. session-harvester 参考结论（细分到哪个点）

实地阅读 C:/Users/yianyao/WorkBuddy/2026-10-05-08-38-51/session-harvester：

- **数据模型三层**：Message（单条消息，最小单位：role/text/timestamp/raw）→ SessionRecord（一个完整会话：source/session_id/title/created_at/messages/extra）→ turn（回合：从一条 user 消息到下一条 user 消息之间的全部消息，读取时的下钻单位）。
- **聚合层 topic（主题）**：topics.py 明确定义「topic = 语义边界由用户裁决的主题（名称+关键词+成员会话证据）；**自动聚类只产候选，不当权威**」。
- **分层读取**：outline（等价 ls）→ read（单会话）→ read --turn N（单回合），按需下钻控制上下文，不整包倾倒。

对 KnowAtlas 的四点启示：

1. 它细分到 **message 级**，比 KnowAtlas 现行条目级细约两级——证明「细粒度入库 + 粗粒度呈现」路线在会话场景成立；KnowAtlas 的 emmx 源（节点级）是同路线的已有先例；
2. 它的 topic 权威在人、自动聚类只产候选——与本方案建议完全一致：块/簇/集做查询期聚合，10 大类人工锚定（KnowAtlas 第五十六批 --cluster-report「只报告不建类」即此口径的落地）；
3. 它的 turn 切分有确定性边界（user 消息）——知识点切分也应优先确定性边界（标题/段落/列表结构），语义切分兜底；
4. 它的 schema 冻结 + meta 库分离 + 同库快照重跑 byte 级一致（可复现红线）——值得 KnowAtlas 借鉴（canary 已有，meta 库分离暂不需要）。

KnowAtlas 侧已落地（第五十七批，正好验证该参考的价值）：adapters/session.py 直接映射 harvester exports 产物（exports/<category>/<YYYY-MM>/*.json = SessionRecord 平铺 JSON），source_key=session_id，turns 摘要入 inline_content，全量对话正文（剔除 note 系统注入轮）落 content_store，每会话一条 source 线程 + conv_messages 全轮次。

## 5. 专业判断：这个模型是否合理

**结论：合理，是当前形态的自然进化方向；但有两个成本风险必须先说清。**

学理依据：用户的模型对应知识管理领域成熟的原子化笔记（Zettelkasten）与常青笔记（evergreen notes）实践——最小单位是单个观点、自底向上聚合而非预置目录。对「整理」和「查找」都正向：命中「点」比命中「文章」有用；同篇不同观点可归不同主题，突破文章单归属局限；单点老化/勘误不拖累整篇。

三个风险：

1. **切分质量无成熟标准**。文章→知识点的自动切分仍是研究前沿，LLM 切分边界不稳定（论点横跨段落、上下文丢失），需人工抽检兜底；
2. **层级语义双轨张力**。10 大类是人工定稿并经真实数据修订的；embedding 自动聚类出的层级没有天然语义（簇名要 LLM 生成），可能与左树脱节成「两套分类系统」；
3. **存量费用**（见第 6 节，结论：钱不是问题，抽检时间是）。

两个关键设计意见：

- **块/簇/集不落库为实体层，作为查询期聚合视图**。实体层要持续维护（聚类漂移后重命名/合并是无底洞）；聚合视图按查询即时计算零维护——延续项目「path 不落库、CTE 派生」的既有哲学（H4 返工教训）；
- **点层独立表（二轮裁决定稿）**：初版曾建议复用 entry 模型（source_type='point'）以零新表；复核后推翻——切片进 entries 会污染左树/词云/时间线/统计/三种导出全部消费面（一篇文章 5 个点 = 词云同词 5 倍权重、时间线 5 根柱、Obsidian 5 条笔记），处处补 `source_type != 'point'` 过滤漏一处即脏数据。改为独立 points 表 + 溯源引用（复用 conv_messages「原文不复制、指针溯源、消费面天然隔离」的既有模式），迁移成本一次，换来全部消费面零改动。

关于「人裁决之后从库中删除」：初版建议 rejected 软删；**用户二轮裁决修订为「即刻不可见 + 30 天冷却 + 自动物理删除」（§5.1 第 4 条）**。

### 5.1 用户裁决记录（2026-10-21 第二轮，定稿依据）

初版方案征询意见后，用户四点裁决（原文要点 + 落地口径）：

1. **书签类单主题文档不切，但呈现必须知识式**——「知识类的内容，就应该是知识本身的聚类显示，而不是搞个不知所谓的标题容器」。落地：组头一律用**成员内容的自身信号**（共享关键词/共享分类/共享 host/代表条目原文摘句——点开组内任一条目可验证），**禁止发明性命名**（「前端工程实践集」这类编造容器名一律不要）；LLM 在聚合中的职责从「起标题」改为「选出成员间真实共享的词」（与「聚类只报告不建类」口径同源）。
2. **知识应该切**——切点后按规范化 content_hash 去重：同一观点多篇重复文章合并为**一个点 + 多条溯源指针**，溯源本身产生新知识（「结论有 N 处独立出处」= 可信度信号；最早出处时间 = 知识形成时间）。点层由此升级为「观点级最小单元」。
3. **真正不该切的是整体型文档**——方案设计类（各部分互相依赖，拆开支离破碎）整条即点；讨论型内容（如小说写法脑图）各条独立成立，才切。落地：切点流水线第一道工序 = **LLM 形态判定**（输出：整体型/集合型 + 一句话理由落 meta），emmx 脑图同样逐个过判定（方案型整图即点、讨论型才切节点）。判定任务便宜（每条输出十几个字），判定理由可抽检归因。
4. **老化终点 = 删除**（推翻初版「archived 归档」建议）——用户理由：过时知识用不上，留着拖慢查找（规模论据：待接入几万封邮件、几 GB 微信聊天记录、≥10 万条 AI 会话，噪声问题会随规模放大）。落地口径（兼顾审计链与引用计数的工程约束）：**人裁废弃 → 即刻 rejected（全部视图/检索/词云/导出不可见，查找体验与删除一致）→ 30 天冷却期 → 自动物理删除**（ksync 顺手清理，含 task_log 处理与 content_store 引用计数）；冷却期 = 误裁决反悔窗口，零操作成本。

另有两项执行者意见一并采纳：**点层用独立 points 表**（不复用 entries 加 source_type='point'——切片进 entries 会污染左树/词云/时间线/导出全部消费面，处处补过滤必漏）；**勘误不篡改原文**（修正以勘误附注层并显，原始层永在——同 55 批摘要哲学）。

## 7. 方案设计

### 7.1 数据模型（点层独立表，块/簇/集查询期聚合）

- **点**：独立 `points` 表（迁移 007_points.sql，canary 同步升版）——
  `id / content_hash（规范化后哈希，去重键）/ text（点正文）/ summary（一句摘要，列表用）/
  source_type（来源载体）/ judge（形态判定：integral=整条即点 / split=集合型切出，含判定理由）/
  created_at / meta`；溯源走 `point_sources`（point_id / entry_id / offset / 定位锚点）——
  **一点多溯源**（同观点重复文章合并后一植多指针），溯源数=可信度信号、最早溯源时间=知识形成时间；
  原文条目永不动、不复制正文（点 text 是抽取产物，原文在 content_store）；
  points 不进 entries_fts/content_fts 触发器体系，点检索走独立索引或查询期 JOIN（开工时定）；
- **块/簇/集**：不落库，查询期按规则（v0.1）或 embedding 语义（v0.2）聚合；
- **类**：现有 categories DAG（10 大类人工锚定）不变。

形态判定流水线（批次 61，用户裁决第 3 条）：

```
每个载体条目 → LLM 形态判定（integral / split + 一句话理由落 meta）
  ├─ integral（方案、论证、单主题文档）→ 整条即一个点（text=inline_content 或全文压缩）
  └─ split（参考集、多主题、讨论记录）→ 切 N 点 → 规范化 hash 去重 → 一点多溯源
```

**增补（2026-10-24，用户裁决 1）· 点的自洽性定义**：

点是"**能自洽的完整内容**"，合格形态只有四种——**带论据的观点/结论**、**概念解释或术语描述**、
**独立完整的步骤**、**独立数据**。不合格：只剩名词的概念、只有一句干巴巴结论无支撑、
被截断的步骤（缺首步或末步）。**一个文件只产 1 个点是合法输出**，不得为凑数而碎切；
反之，一个文件里若有多条互不依赖的完整知识，也不得强行合成一点。
验收：随机抽 20 点，人工判"脱离原文件能否独立读懂"，目标 ≥90%。
落地：`point_extract` prompt 增自洽性纪律 + `pipeline/points.py` 守门（裸名词、步骤截断判定），见 TODO Phase 8.5。
**已实施（2026-10-24）**：`pipeline/point_gate.py` 确定性闸门（过短/裸名词/步骤缺首·跳号·缺尾/
尾部截断/代码块未闭合）；`point_extract` 三份 prompt 增自洽性纪律并允许 `points: []`（无可独立
成点，不算故障）；`points.py` 逐点过闸、全拒条目记 `meta.points_gate` 防重复烧钱、`kpoints
--retry-blocked` 重抽。真实库 27 点零误杀、6 类反例全拦。"一句干巴巴结论"不做机器判定（与单句
术语定义不可分），交 prompt + 人工抽检。详见 `变更工单-2026-10-24-8.5自洽性闸门.md`。
裁决原文与配套口径见 `需求澄清与裁决-2026-10-24.md` §3。

### 7.2 右边列表改「知识集」（用户裁决第 1 条：组头信号化）

三种集的来源并存：

a. **系统聚合集**（查询期）：检索命中按「主分类+同 host」（v0.1，零费用）或语义聚类（v0.2）聚成组——**组头 = 成员内容的自身信号**（共享关键词/分类/host/代表条目原文摘句），禁止发明性命名；LLM 只做「选出成员间真实共享的词」，不做标题创作；
b. **人工线索**（threads，已实现）：用户固化的集，检索视图已有「线索」页签可查；
c. **源原生结构集**：邮件/AI 会话线程（conv_messages 已还原）、重灌后的 emmx 方案型脑图（整图即点挂 mind_path）——天然就是「集」。

列表形态：从「平铺条目卡片」改为「集分组列表」——组头（信号词 + 条目数 + 代表条目内容摘句），组内条目卡片保留来源徽标作为元信息（不再作为组织维度）。第五十六批 embedding 已落地，v0.1 即可用 sim 通道 + 贪心聚类 + 信号词提取（--cluster-report 实现复用，接入列表视图）。

### 7.3 分层查询（点/块/簇/集/类）

渐进披露：命中少（1-5 条）→ 直接给点；命中多 → 先给集概览（每集：信号组头 + 成员数 + 代表条目），点集内下钻到点。查询按关键词精确度返回对应层级：精确关键词给点、主题词给簇/集、泛词给类（复用分类导航，不新做）。与现有工作台视图合并为页签化检索视图。

### 7.4 关系图纯层级下钻模式

现有 showSubtree 改「层级模式」开关：点分类只出下一级子分类（不出条目），条目在叶子层或显式「显示条目」时出现；实现用户 4.1-4.3 的逐层钻取。前端改动为主，零数据成本。此为独立小批（先于知识模型大工程）。

### 7.5 老化三级（出口=删除，用户裁决第 4 条）

- L1 代码（已有）：freshness.py 规则（keyword→stale / date_old·newer_version→suspect）；
- L2 LLM（新增）：对 suspect 逐条问「是否过时+理由+建议」（batch 20，降级纪律同 delta_summarize），结论升级 stale 或否决；LLM 知识截止之后的新版本它判不了——判不了的自然下沉到人，与三级设计自洽；
- L3 人（新增）：时效候选区加「确认废弃」按钮 → **即刻 rejected**（全部视图/检索/词云/导出不可见，查找体验与删除一致）→ **30 天冷却期 → 自动物理删除**（ksync 顺手执行：rejected 且 rejected_at 超 30 天的条目连 task_log 关联一并清/归档，content_store 按引用计数回收——多条目共享同一内容块时只减计数）。冷却期=误裁决反悔窗口，零操作成本；「清空拒绝区」手动按钮可选加。

**规模前瞻**（用户裁决论据）：待接入几万封邮件、几 GB 微信聊天记录、≥10 万条 AI 会话（conv_messages 可达数百万行）——删除出口必须真删，拒绝区只作冷却缓冲不作长期存留；检索/聚合查询在批次 61-65 期间持续以真实库规模压测，10 万条规模下查询期聚合需签名缓存（词云挂账同款），届时立项。

### 7.6 勘误三级（全新，附注层不篡改原文）

- L1 代码：**只做确定性错误**（完整代码块语法验证、死链 link_status=dead 已有、API 名与版本号对照表）；代码片段多为节选，ast/compile 对疑似错误一律不下结论交 LLM——L1 误报会把人淹没并毁掉功能信誉；
- L2 LLM：事实一致性核查（「该说法在当前版本是否仍然成立」），**结论必须附可核查依据（官方文档 URL/版本号），给不出依据只能标「疑似」，永远不到「确认错误」级**（防 LLM 幻觉直接废掉正确知识）；
- L3 人：裁决 → **改正 or 废弃**（同 7.5 出口）。**改正 = 勘误附注层**：修正文字挂点/条目（errata 字段或勘误线程），展示时原文+勘误并显，原文永不改写——溯源链保住（点引用的原文变了勘误依据就丢），同 55 批「摘要是附加层、原始层永在」哲学；知识真要更新，正道是新知识入库 + 旧知识老化废弃。

### 7.7 布局改造（三层信息架构，mockup 已出；58 批左栏折叠已落第一步）

- 顶栏：品牌 + 全局搜索 + 「＋收录」（悬停/展开说明「同 kadd：抓正文→归类→索引」）+ 设置；
- 页签行：检索（默认）/ 关系图 / 串联 / 词云 / 时间线 / 管理——每个视图全屏，不再堆在侧栏（现有工作台三视图切换即其基础）；
- 左栏：仅分类树 + 底部 bookmarklet 拖拽条（说明「在任意网页点一下即收进库」）；58 批已做默认折叠+悬浮条搜索镜像+[ 快捷键，页签化是其终态；
- 管理页（第六页签）：暂存区、待清理、失效链接、时效候选、数据管理（各源配置状态）——日常消费页从此干净。

### 7.8 emmx 全删重灌（用户二轮裁决：此前切分过碎，推倒重来）

**背景**：用户怀疑此前入库把不该切的切了（方案型脑图被拆成节点条目，方案整体性尽失），裁决干脆全删、按新模型重新全量入库。

流程（批次 62）：

1. **备份**：重灌前强制 kbackup 快照（VACUUM INTO，含全部 emmx 条目与 mind_path meta）；
2. **全删**：按 source_type='emmx' 清除条目（含 entry_categories 挂接、content_store 引用计数回收、task_log 留痕「emmx_rebuild」批次标记）；
3. **适配器改造**：adapters/emmx.py 加形态判定——每 .emmx 文件先 LLM 判定 integral/split（判定依据=脑图主题+一级分支内容，理由落 meta.judge）：integral（方案型）→ 整图一个点（节点树压缩为结构化大纲入点 text，mind_path 保留）；split（讨论型）→ 节点照旧切条目（现行逻辑）；
4. **重灌**：ksync emmx 全量重跑（判定费 ~800 条 × 十几个字输出，可忽略）；抽检 20 个文件核对判定与切分质量（重点：方案型是否保住整体性）；
5. **验收探针**：重灌后 emmx 条目中 integral 型整图成点（无节点碎片）、split 型节点条目挂 mind_path；判定理由可查；总条目数 ≤ 原 802（方案型收敛）。

### 7.9 知识梳理（合成层，2026-10-22 用户裁决：回灌+隔离）

**背景**：用户提出「知识的梳理」——勾选若干知识点调用 LLM（默认提示词可修改、人确认）生成新方案；以及点→块→簇→集自动重排生成新导向图。同日评估裁决：三件事拆开——**勾选合成高价值，做**；**全自动重排固化降级为梳理预览**（错误成本不对称，emmx 误判同款教训：预览错了划走即可，固化错了要拆）；**AI 配图不做**（不可溯源）。

**核心裁决**：生成物**回灌知识库**（成为可检索条目、参与后续聚类与集分组）+ **隔离**（绝不混入原始条目体系，否则溯源链被 LLM 产物污染、全库可信度崩塌）。

设计：

1. **合成条目**：新 `source_type=synthesized`——生成物为独立条目，原始层零改动；
2. **强制溯源**：`meta.sources=[point_id/entry_id…]`，生成内容可回跳来源点（防幻觉闸门同款：无溯源不出库）；
3. **提示词面板**：按选中对象预填默认模板，可修改后提交（表单级成本）；
4. **人确认闸**：勾选（即人审入口，触发天然限量）→ 提示词面板 → 预览（不落库）→ 确认后落库；
5. **老化出口**：合成条目走 §7.5 同款人裁废弃→30 天冷却→自动物理删除（来源劣化/观点过时可回收）；
6. **交互流**：检索/集分组视图勾点 → 「梳理」按钮 → 提示词面板 → 预览 → 确认 → 挂 threads（人工线索，现成固化集）或存 synthesized 条目。

**明确不做**：①点→块→簇→集全自动重排落库固化——§7.1「块/簇/集查询期聚合不落库」的既定设计不推翻；重排结果仅作投影视图（可看可导出），人觉得好才固化为线索（threads 零新增表）；②AI 配图；LLM 产出一律 Markdown。

费用：勾选即人审天然限量，~¥0.01-0.03/次，月几十次 <¥1。
