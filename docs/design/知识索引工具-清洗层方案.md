# 知识索引工具-清洗层方案

> 创建：2026-10-24（批次 97 立项，用户裁决「任何源抓了正文之后，第一件事就是清杂质」）。
> 定位：统一管线「抓正文 → **清洗** → 入库条目 → 提炼点 → 向量」的第 ① 步设计。
> 上位方案：[知识索引工具-知识集与知识生命周期方案.md](知识索引工具-知识集与知识生命周期方案.md)、[知识索引工具-SOP.md](知识索引工具-SOP.md)。

## 1. 设计原则（用户裁决 + 成熟方案调研结论）

1. **清洗前置**：任何源，抓到正文后第一件事过清洗——垃圾不进库，不靠后置打标兜底。
2. **两段式**：`解析段`（per-source，格式专属）→ `通用噪音段`（全源共用）。解析段把格式变成「干净的结构」，通用段把「结构里的杂质」剔掉。
3. **解析不重造轮子**：办公/PDF 用 MarkItDown，HTML 用 trafilatura，旧版 Office 走既有 office_legacy，邮件引文剥离走既有 quote_strip——每个选型都经调研核实。
4. **宁缺毋脏**：清洗后无实质内容 → 拒收（degraded 打标），绝不把空壳入库。
5. **可反悔可溯源**：清洗动作记 meta（clean_flag / clean_note），原始 content_store 永不覆盖（清洗只影响入库正文视图，原文保留用于追查误杀）。
6. **噪音源进缓冲**：AI 会话 / 微信记录等高噪音源清洗后默认进 pending 缓冲区（既有裁决），人工确认才进消费面。

## 2. 通用噪音清洗段（clean_common，全源共用）

新增 `pipeline/clean.py`，两件套：

### 2.1 clean_common(text, cfg) -> CleanResult

阈值全部 dataclass 承载（`CleanThresholds`：min_body=50、repeat_line_max=5、
index_line_min=10、url_only_min 等默认值），配置文件可覆盖、测试可注入——
不硬编码（不同库容忍度不同）：

| 规则 | 说明 | 现状 |
|---|---|---|
| ① 零宽/控制字符 | \u200b-\u200d/\ufeff/\r 归一、控制符剔除 | 散落各处，收编统一 |
| ② 重复行剔除 | ≥10 行且互异行占比 ≤40%、某行重复 ≥5 次 → 判目录索引页 | 批 94 已有（骨架检测内），提升为独立步骤——重复行**剔除**而非整条拒绝 |
| ③ 骨架信号守门 | 五路信号（行级/短语级/结构标签/重复行/GitHub 模板）判中 → 拒收 | fetchers/base.py 已有，复用 |
| ④ HTML 实体残留 | `&nbsp;/&lt;/&#x1F600;` 实体解码；解码后仍是骨架 → 拒 | 新增（解码单独做，别把「教 HTML 的文档」误杀） |
| ⑤ 噪音行剔除 | URL-only 行、纯符号行、超长 Base64/哈希行（>200 字符无空格） | 新增 |
| ⑥ 最小实质守门 | 清洗后 <50 字符（对齐 _MIN_BODY_CHARS）→ 拒收 | points 管线已有口径，前移到清洗 |

返回 `CleanResult(cleaned_text, removed_chars, flags)`；flags 进条目 meta 供人工核查。

### 2.2 redact（脱敏段，独立于清洗——借鉴 logminer 五段式）

**redact 是独立阶段**（parse → redact → clean → evaluate → filter），不是
clean_common 的子规则——脱敏错漏是安全事故，与「清不干净」不同责：

- **触发源**：AI 会话（§3.4）、微信（§3.8）、邮件（§3.5）三个高泄漏面默认启用；
  其他源关闭（本地文件/书签无此风险，误脱敏反而破坏知识）；
- **规则**（规则清单可配置）：API key/token 模式（sk-、ghp_、AKIA、JWT 形态）、
  手机号/身份证（正则 + 校验位）、邮箱地址（保留域名形态、遮本地部分）、
  IP/内网地址；命中 → `█` 遮蔽 + meta.redact_count 计数（可审计不可逆——
  原文 content_store 不脱敏，仅入库正文视图脱敏，原文访问走既有权限模型）；
- **夹具纪律（重要）**：§6「真实数据入测试夹具」前必须先过 redact——
  隐私/密钥不得写进仓库。

### 2.3 去重收口（重复内容同样属于「垃圾不进库」）

三层既有体系（入库 canonical / 点 content_hash / 提炼显式去重）管 URL 级与
点级；本方案补**条目内容级**一层，落在 sync._apply_content 收口点：

- 清洗后正文 SHA-256 与既有条目比对——命中且源不同（邮件转发重复投递、
  OPML/书签多路径收录同一文章、重同步差分漏网）→ **不新建条目**，
  locator 附挂到既有条目（attach_locator 既有机制，双 locator 可跳转）；
- 验收标准加一条：**真库重同步，重复条目零新增**。

## 3. 分源方案

### 3.1 办公软件（docx/xlsx/pptx + 旧版 .doc/.xls/.ppt）

- **解析段（双链路，踩坑已固化）**：
  - 新格式 docx/xlsx/pptx → **MarkItDown** 转 Markdown（表格保结构、页眉页脚剔除）；
  - 旧版二进制 .doc/.ppt/.xls → **office_legacy 既有链路**（LibreOffice soffice headless → Windows COM → 报错给指引），markitdown 无此转换器（[迁移踩坑清单 §1](../迁移踩坑清单.md)）。
- **清洗段**：MarkItDown 产物过通用段 + 两条专属规则——页眉页脚重复行（每页重复的同一行剔除，复用②逻辑按「跨节重复」判定）、连续空段落压缩。
- 落库形态：Markdown 文本；xlsx 多 sheet → 各 sheet 以标题分段（`## Sheet名`）。

### 3.2 PDF

- **解析段**：文本型 → MarkItDown（内建 pypdfium2）；优先级低于 docx（PDF 版式噪音天然多）。
- **能力上限（明记）**：MarkItDown 对 PDF 是无 layout model 的薄封装——多栏/表格/公式版式保真度有限。
  **升级路径**：MinerU（CJK 最强、CPU 可跑）或 Docling；**量化触发条件**：真库扫描件占比 >10%
  或用户版式失真投诉 ≥3 例时立项（不是泛泛的「等真实需求」）。
- **清洗段**：通用段 + 专属规则——页码行剔除（独立数字行）、连字符断行合并（行尾 `-` + 行首小写）、扫描件判定（提取字符数/页面积比过低 → **诚实拒绝**，打 `body_flag=scanned_pdf`，不 OCR——OCR 质量不可控且费用高，触发条件见上行升级路径）。

### 3.3 万兴脑图 .emmx

- **解析段**：已有 adapters/emmx.py `parse_tree()`（嵌套树、断链按顶层、防环）。
- **清洗段（新增剪枝规则）**：
  - 空节点/纯符号节点剔除；
  - 单支链合并（A→B→B1→B11 且 A、B 无子 → 合为 A→B1→B11）；
  - 纯装饰节点（图标占位/链接壳节点）剔除；
  - 节点文本过通用段（脑图节点常带富文本残留）。
- 纪律沿用批次 92 口径：**整图即一点**，剪枝只影响树的阅读形态，不产生碎片条目。

### 3.4 AI 会话轨迹（高噪音，pending 缓冲）

- **解析段（新建 adapters/aichat.py）**：导出 JSON → 对话轮次流 → 落 conv_messages（**复用邮件的 threads/conv_messages 架构**，thread_type='source'——表结构迁移 003 已就绪，当时设计即「会话复用邮件线程还原」）。
  - **树状分支处理**（ChatGPT conversations.json 是树）：编辑/重生成留废弃分支——**沿 current_node 回溯取主干**，废弃分支不入库（业界工具共识）。
- **清洗段（轮次级，按平台适配）**：
  - 思考块剥离**按平台适配**（不宜一条正则通用）：DeepSeek-R1/o1 系 `<think>…</think>`；Claude 系结构化 `type:"thinking"` 块；Gemini 系 thought 标记——适配器按导出来源分派；
  - 剔工具调用残留（function_call 块、`tool_use` JSON、"Running tool…" 行）；
  - 剔悬空意图句——**带保护条件**：仅当轮次剔除意图句后剩余 <N 字符（N 走 CleanThresholds，默认 20）才剔——「我打算分三步做」本身就是内容，防误杀；
  - 剔寒暄 filler（「好的，明白了」「当然可以」开头的独立轮次）；
  - 轮次正文过 redact（§2.2）→ 通用段。
- **纪律**：清洗后默认 pending 缓冲（既有裁决——新条目不直接进消费面，人工确认放行）；会话标题/模型/时间进 meta 溯源。

### 3.5 邮件

- **解析段（已有，第三十九批）**：maildir 适配器 + 线程还原（In-Reply-To/References + Subject 归一）→ threads/conv_messages。
- **清洗段（已有 + 补丁）**：
  - 引文剥离 quote_strip 已有（mail-parser-reply 底座 + 中文回复头「在…写道：」「------ 原始邮件 ------」自补规则）——**不引入新库**（调研确认 email-reply-extractor 与之重叠）；
  - **补丁：furniture 剔除清单**（借鉴 email-reply-extractor 两段式第二段）——签名块（`--` 分隔线后的姓名/职位/电话块）、列表页脚（unsubscribe/“您收到此邮件因为…”）、移动端标语（「发自我的 iPhone」）、法律免责声明（「本邮件及其附件含有…保密」）。
- 落库形态：剥离后正文 = 条目正文；被引用轮次进 conv_messages 溯源。

### 3.6 HTML / 网页（书签源、手工收录、GitHub 扩散共用）

- **解析段（换装）**：readability-lxml → **trafilatura**（调研结论：主干提取评测全面优于 readability，boilerplate 去除是本职；readability 降级为 trafilatura 失败时的回落）。raw.githubusercontent 直链纯文本直取不变。
- **清洗段**：trafilatura 自带 boilerplate 清洗 + 通用段（骨架五路信号做二道守门）+ 批 94/95 既有拦截（文件名黑名单、GitHub 模板信号）不变。
- 前置层不变：L0 价值守卫（URL 结构）仍在分类管线，黑名单在扩散候选层。

### 3.7 腾讯文档 / IMA 文档

- **腾讯文档（路径修正——调研核实）**：个人版**无公开内容 API**，官方通道只有网页端
  「≡ → 导出为 → 本地 word/sheet/slide」。链路定为：**官方导出 → 汇入 §3.1 办公链路**
  （导出目录配成 folder 源即可，零新代码）；企业版开放平台接口需资质前提，待有资质再议。
  SOP §2.12 的 OpenAPI 凭证描述按此修正。
- **IMA**：零转换 MD 直读（风险最低），过 redact 评估后走通用段即可。
- **评论线程**：腾讯文档导出若含评论，**不清洗不剔除**——评论是协作上下文，进 conv_messages（等同邮件轮次）。

### 3.8 微信聊天记录（高噪音，pending 缓冲）

- **解析段（新建 adapters/wechat.py）**：外部工具（MemoTrace 活跃 fork）产物目录扫描（既有契约不变）→ 消息流；按会话对象 + 自然日还原线程。
- **媒体文件处置（明确）**：MemoTrace 产物含图片/语音目录——图片/语音/视频**只留路径清单进 meta、不进正文**（收作资产是独立决策，不默认）；语音消息打「待转写」标记（转写方案未立项，先留钩子）。
- **清洗段（轮次级，调研清单四类）**：
  - 无意义短句剔除（「好」「谢」「收到」「哦」类弱语义 + <5 字符含弱语义词）；
  - 表情包/[图片]/[链接卡片占位]剔除；
  - @消息保留内容但剥离 @ 标记；系统消息（撤回/入群/拍一拍）剔除；
  - 纯 URL 消息转「链接待抓取」候选（走 §3.6 HTTP 管线）而非垃圾文本；
  - 消息正文过 redact（§2.2）→ 通用段。
- **已知取舍（注明）**：「按日线程化」会切断跨天连续对话——按日是可浏览性与上下文完整性的折中，跨天重要对话依赖 threads 的会话对象聚合兜底；将来若有真实痛点可改为「按静默间隔切分」。
- **纪律**：pending 缓冲（既有裁决）；落 conv_messages（同 §3.4 架构）。
- **图片处理子案（将来立项，先看情况）**：海量聊天截图的挖掘可行性已评估——技术无空白区，
  难度在成本控制不在算法。分两级漏斗：
  - **P1 初筛（零 LLM 成本，可全量跑）**：pHash 感知去重（imagehash，同图多次转发）
    → 截图/照片分类初筛（手机截图版式特征：状态栏/对话气泡/文本块，轻量启发式或
    小模型即可，照片/表情包淘汰）→ PaddleOCR det 文本检测（只检不识，CPU 几百
    ms/张）→ OCR 识别 → 字数/骨架规则打标；
  - **P2 价值判定（LLM 成本，限量跑）**：P1 候选过既有价值判定管线（L0 守卫 + 骨架
    信号 + LLM 判定）→ 有知识价值的进提炼；产出**进 pending 缓冲**（截图脱离对话
    上下文，知识可信度天然低，人工确认放行）；
  - **已知坑（立项时直面）**：①聊天截图字体小/分辨率低，OCR 错字会进知识（数字/
    代码/人名尤甚）；②截图脱离对话线程，出处无从考证——P2 产出一律缓冲；
  - **触发条件**：P1 随时可为（零成本）；P2 等真实需求（截图知识人工翻查痛点出现
    时限量跑）。

### 3.9 B站视频（条目同步保留，内容清洗暂缓）

- 用户裁决：字幕单拎出来没用（无耳无眼总结不了），**内容清洗暂缓**。
- 收藏夹同步条目照常入库（标题/简介/UP主/链接 meta），正文留空不打点；清洗层不做视频转写。将来若接 whisper 转写再立清洗子案。

### 3.10 OPML 订阅

- **现状修正**：OPML 导入回路已实现（第五十批，ksync 批量源），大纲树往返保真——**不是新源，是已有源**。
- **清洗层的活**：OPML 条目的正文抓取（xmlUrl 指向的文章）走 §3.6 HTTP 管线（trafilatura + 通用段），无专属清洗规则；抓取失败条目进失效链接区（既有裁决）。
- **量级约束（防首轮爆炸）**：订阅源历史归档可能成百上千篇——首轮抓取限「每源最近 N 篇」（N 配置化，默认 20），更早的归档不自动抓、按需手动补；增量同步只抓新条目。与失效链接区策略衔接。
- OPML 文件本身的 outline 结构 = 条目分类先验（L1 priors 直接吃 outline 树）。

### 3.11 folder 本地文件（text/md/代码等）

- file_reader 读取后过通用段（当前零清洗的最大缺口，直接补）；
- 代码文件不做语义清洗（代码是知识本体），只过 ① 控制字符；README/文档类过完整通用段。

## 5. 分批实施序（批 97 起步，每批可独立验收）

1. **批 97a：通用段 + redact + 收口**——clean.py 建成（clean_common + CleanThresholds
   + redact），sync._apply_content 插桩（清洗 → 脱敏 → 内容 SHA-256 去重收口），
   file_reader/http_simple 接入，trafilatura 换装；**IMA 一并接入验收**（零转换 MD
   直读，早拿一个真实源验证通用段——评审建议采纳）。验收：真库重同步垃圾/重复条目零新增。

   官方导出目录即走此链路（零新代码）。验收：真实 docx/pptx/PDF 各一枚入库。
3. **批 97c：邮件 furniture 补丁 + emmx 剪枝**（邮件接入 redact）。验收：真库签名
   邮件剥离前后对比、脑图剪枝树对比。
4. **批 97d：AI 会话适配器**（分支主干 + 平台思考块 + 轮次清洗 + redact + 缓冲）。

5. **批 97e：微信适配器**（媒体处置 + 四类剔除 + 按日线程 + redact + 缓冲）。
   验收：真实聊天记录清洗前后对比。
6. OPML 量级约束随 97a 的收口顺带落（每源最近 N 篇）；B站不动。

| 原设计 | 实现 |
|---|---|
| ① 零宽/控制字符 | `_normalize`（零宽、行尾空白、连续空行、连续分隔线） |
| ② 重复行剔除（目录索引页） | 拆成两条：**目录点线块**（`_drop_toc`，要求点线 + 末尾页码，≥3 条）与**重复页眉页脚**（`_drop_repeated`） |
| ③ 骨架信号守门 | 既有 `fetchers/base.py` 不动；新增 `is_navigation_doc`（navbar/sidebar 这类纯链接表整篇判非知识） |
| ④ HTML 实体残留 | 随 97a+（trafilatura 换装）一起做 |
| ⑤ 噪音行剔除 | 落成**页码行**（占比自适应）+ **推广尾**（窗口 + 上限）+ **导航文件** |
| ⑥ 最小实质守门 | 不动（`_MIN_BODY_CHARS` 既有口径），清洗后为空由 L0 打 not_knowledge |
| redact | 独立函数，`[clean].redact_enabled` 控制；**证件规则必须排在手机号之前** |

**三处必须记下来的修正**（都是真实数据打出来的）：

1. **重复行不能按"完全相同 ≥3 次"删**。实测第一版把 `)`（235 次）、`}`（180 次）、三引号（216 次）
   当页眉整批删除，`agentic-design-patterns` 保留率跌到 0.856，被放弃闸门拦下——整本书等于没洗。
   现在要过三重判据：**像散文**（4–40 字、含 ≥2 汉字或 ≥6 字母、不以代码符号结尾）+
   **行距周期性**（相邻间隔的变异系数 ≤0.45，页眉按页重复）+
   **非结构性**（单行出现次数 ≤ 全篇 2%，否则是"每章都有小节名"这类结构，不动）。
2. **放弃闸门默认值从 0.90 降到 0.80**。页码重的书正常就会删 10–15%，0.90 会让"洗对了"的文档被判失败。
3. **低占比独立数字行按设计保留**。页码规则要求占非空行 ≥2% 才动；低于阈值的（如 `1`/`2`/`3`）
   可能是编号或数据，宁可留。5 篇 PDF 因此各留 ≤1%，由 97b（有页边界信息）再收。
4. **兜底阈值只能有一个来源**。`sync._clean_options` 第一版把 `min_keep_ratio` 兜底抄成 `0.90`，
   而 `CleanThresholds` 默认已改 0.80 → 配置里没写 `[clean]` 时，0.856 的书每轮都被判"洗太狠"退回原文，
   现象是"清洗跑了，库没变"。现在兜底直接取 `CleanThresholds().min_keep_ratio`。
5. **百 MB 级 PDF 没有上限**（97a 暴露、97b 待修）：`Hello-Agents` 97.9 MB 单文件解析 **25 分钟**，
   `厦门大学…882页` 51 MB 跑 8 分钟仍未完、被中止。现有 pdfplumber 链路是纯 CPU 解析，
   需要按"页数/字节数 + 超时"设闸门：超限 → 打 `degraded` + 进待清理，不阻塞同步。

**验收结果（20 份真实正文 / 105,846 行）**：噪声 4,896 行（页码 2,578、目录 1,555、重复行 751、推广 10），
正文行保留率 0.9999；`agentic-design-patterns` 页码 1,347→0、目录 273→0；`agentic-ai-guide` 目录 994→0；
`Harness`/`Obsidian-AI` 推广尾→0；`雪花写作法` 零删除。

**未落（顺延）**：trafilatura 换装 → 97a+（用户 2026-10-24 认可：不与规则清洗同批改，避免两个变量混淆归因）；
IMA 验收 → 8.12（本机无凭证）；HTML 实体解码随换装一起。

## 6. 验收纪律（每批必做）

- 清洗前后 diff 样例（真实数据，**入夹具前必过 redact**——隐私/密钥不得进仓库）；
- 误杀检查：教 HTML 的文档、含签名但正文有实质的邮件、含「我打算分三步做」的
  实质轮次不得被误剔（测试用例固化）；
- 通用段单元测试（阈值经 CleanThresholds 注入）+ 各源集成测试；全量 pytest +
  字节扫描（UTF-8 无 BOM + LF）；
- 真库重同步探针：清洗前后条目数/垃圾率/**重复条目数（应为零新增）**对比写入
  夜跑计划文件。
