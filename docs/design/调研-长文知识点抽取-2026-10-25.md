# 调研：长文档怎么抽知识点（业界做法 + 本项目落点）

> 2026-10-25。回答"一本 67 万字的书只抽出 1 个点，别人怎么处理"。
> 结论先行：**长文必须分块 + 每块抽原子知识点 + 跨块去重合并**；"整篇一个点"
> 在业界没有这种做法，只有"整篇摘要"（那是另一种东西）。本文只做调研与方案，
> 未改代码。

## 0. 先分清两个东西：摘要 ≠ 知识点

- **摘要（summary）**：一章/一本书讲什么，一段话概括。RAPTOR、map-reduce
  summarization 做的是这个，粒度是"文档/章节"。
- **知识点（knowledge point / proposition）**：可独立复用的原子陈述，
  粒度是"一句到一段"。Dense X Retrieval 的定义：*atomic expressions within
  text, each encapsulating a distinct factoid, concise and self-contained*。
  这正是用户裁决 1 要的形态。

现在的实现把两者混了：integral 路径让 LLM 对 4,023 字"提炼成一个知识陈述"，
产出的是**摘要**，不是知识点。

## 1. 业界怎么做（有出处的四条）

### 1.1 分块：结构优先，大小兜底

- **Microsoft GraphRAG**（默认配置）：按 token 切块，**size=1200、overlap=100**；
  支持 `prepend_metadata`（把 title 等文档字段拼到每块前面），然后**逐块**做
  LLM 抽取，再跨块汇总同一实体的描述。见
  `graphrag/config/defaults.py` 的 `ChunkingDefaults` 与
  [Indexing Methods](https://microsoft.github.io/graphrag/index/methods/)。
- **Chroma 技术报告**（2024-07，[Evaluating Chunking Strategies](https://www.trychroma.com/research/evaluating-chunking)）：
  在 token 级召回/精度上，`RecursiveCharacterTextSplitter` **200–400 token、
  不重叠**往往就很好；语义分块（embedding 断点）收益不稳定，LLM 分块召回最高
  但慢且贵。结论：**别为分块再上一次 LLM**。
- **Anthropic Contextual Retrieval**（2024-09）：块脱离全文会丢上下文（"该公司
  营收增长 3%"不知道是哪家公司），做法是给每块**前置一段 50–100 token 的
  上下文**再建索引；检索失败率降 35–49%。对我们的映射：点必须自包含，且抽取时
  把"书名/章节路径"作为上下文一起给 LLM。

### 1.2 抽取粒度：proposition 级优于 passage 级

- **Dense X Retrieval**（arXiv:2312.06648）：把文档重写成 **proposition**（原子、
  自包含的陈述）再索引，检索与下游 QA 都显著优于 passage 级。做法就是让 LLM
  把段落改写成一组 proposition。
- 教材知识图谱方向（K12 数学知识点标注 arXiv:2208.09867、MathScale
  arXiv:2403.02884）也是先抽"知识点/概念"再建概念图，而不是"一章一个点"。

### 1.3 跨块合并：抽取 → 归并 → 去重

- GraphRAG 对同一实体/关系在不同块里的描述做 **summarize_descriptions** 合并；
  抽取阶段还有 `max_gleanings`（再问一遍"还有吗"）提升召回。
- 对我们的映射：同一知识点在相邻块重复出现时，用**规范化 hash（已有）+ 可选
  embedding 相似度**归并；不重复建点。

### 1.4 层次化：书 → 章 → 节（可选，后置）

- **RAPTOR**（arXiv:2401.18059）：递归聚类 + 摘要建树，检索时跨层取。
  这适合"整本书讲什么"的问答/导航，**不能替代**原子知识点；本项目可放到
  8.6 三视图验收时做"书/章摘要层"。

## 2. 本项目现状与差距

| 现状 | 业界 | 差距 |
|---|---|---|
| 点抽取只读 `inline_content`（4,000 字 + 截断标记） | 全文分块（1200 token 级） | 一本 67 万字的书只看到 0.6% |
| 长文默认 integral → "恰好一个点" | 逐块抽 1–8 个原子点 | 粒度错（摘要在冒充知识点） |
| 无章节/块元数据 | 每块带 title/章节上下文 | 点无法回溯到"第 4 章 4.1 节" |
| 无跨块合并 | 抽取→归并→去重 | 长文重复内容会重复建点（现在因为只抽一次反而没暴露） |
| 前言/目录照抽 | 分块 + boilerplate 过滤 | "本书定位与写法"被当知识点 |

## 3. 建议方案：结构感知分块 + 逐块命题抽取 + 归并

### 3.1 两条分块路径（按源文本形态）

1. **有标题结构的文本（.md/.html 转 md）**：按 `#`–`######` 标题切"节"，
   **代码围栏内的 `#` 不算标题**；单节超过 `CHUNK_MAX`（建议 4,000–6,000 字）
   时按段落再切，边界留 10% 重叠；过短的节（<300 字）并入相邻节。
   → 每块带 `section_path`（如 "第4章 > 4.1 多智能体架构 > 4.1.1 决策与控制"）。
2. **无标题结构（PDF/纯文本）**：按段落/句子窗口切 4,000–6,000 字，
   10% 重叠；块序号 + 首行作为 pseudo-section。PDF 的目录/封面由 front-matter
   过滤处理（见 3.3）。

不引入 embedding 语义分块（Chroma：收益不稳定），也不让 LLM 分块（贵且慢）。

### 3.2 逐块抽命题

- 输入：`标题 + section_path + 块 i/n + 块正文`；
- 输出：**1–6 个**知识点（不是 1 个），每条满足 8.5 自洽性纪律，带 `quote`；
- 允许空（本块是过渡段/目录）；
- 现有 `point_gate` 继续逐点过闸；
- 记录 `meta.section_path`、`meta.chunk_index`、`meta.chunk_total`、
  `meta.char_start`（点在原文的大致位置，配合 quote 溯源）。

### 3.3 前言/目录过滤（C）

- 标题命中：`目录|前言|序言|序|关于本书|版权|致谢|附录|Preface|Contents|Copyright`；
- 或内容特征：点线目录（`. . . .`）、大量页码、无标点短行占比高；
- 命中 → 该节**不抽点**，落 `meta.front_matter=true`（可查、可人工覆盖），
  不算失败；PDF 的封面/版权/目录通常正好在第一块。

### 3.4 归并与去重（B）

- 块内/跨块：`normalize_point_text` + `point_hash` 去重（已有）；
- 近重复（可选，需 embedding）：同一条目内 cosine > 0.92 视为重复，
  保留字符更长/quote 更完整的一条；没有 embedding 时先只做 hash 去重；
- 跨块重叠区产生的半句由 `point_gate` 拦截（截断/过短）。

### 3.5 与现有形态判定的关系

- 短文档（≤ `SINGLE_POINT_MAX`，如 6,000 字）保留 integral 单点（一篇短文
  一个点合法）；
- 长文档不再问 LLM"整篇给一个点"，直接走分块；`split`/`integral` 的目录规则
  降级为"是否分块"的启发式，不再决定点数；
- 文学创作（雪花写作法）继续 split，但同样受 `CHUNK_MAX` 约束（它本身只有
  6,000 字，不受影响）。

### 3.6 成本估算（按当前 key）

- 语料 5.9 M 字符，按 4,000 字/块 → ~1,500 块 → ~1,500 次调用；
- DeepSeek-V4.1-Flash：输入 $0.15–0.30/M tokens、输出 $0.60–1.20/M tokens
  （off-peak/peak，见官方 pricing）；5.9 M 字符 ≈ 4–6 M input tokens，
  输出 1–2 M tokens → **全量一次约 $2–5**；
- 先拿 1 本书（Hello-Agents，67 万字）做 A/B：约 170 块，成本 < $1。

## 4. 不建议做的事

| 做法 | 为什么不做 |
|---|---|
| 把整本书（67 万字）一次性塞进 1M 上下文 | 模型上下文够，但"中间丢失"（lost in the middle）+ 无法给出章节级溯源 + 一次输出会被压成摘要；分块可并行、可重试、可定位 |
| embedding 语义分块 | Chroma 实测收益不稳定，多一层模型依赖 |
| LLM 直接分块 | 慢、贵、可能改写原文；标题结构已经够用 |
| 用 RAPTOR 摘要树替代知识点 | 摘要回答"书讲什么"，不回答"有哪些可复用知识"；可后置为浏览层 |
| 继续用 integral 单点覆盖长文 | 就是现在的问题 |

## 5. 分步落地建议（每步可独立验收）

- **B1（核心，先做）**：全文可见 + 结构分块 + 逐块抽点 + hash 去重 +
  章节元数据 + 统计（块数/调用数/去重数/空块数）+ 单测（分块边界、代码围栏、
  重叠、去重、幂等）。
- **B2（小）**：front-matter 过滤（标题黑名单 + 目录特征），PDF 首块验证。
- **B3（后置，8.6）**：书/章聚合层与摘要（RAPTOR 式可选），检索/关系图按书下钻。
