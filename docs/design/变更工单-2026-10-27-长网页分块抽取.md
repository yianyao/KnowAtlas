# 变更工单：长网页分块抽取（在管道内切块，取代「长文一律交 kpe」）

- 日期：2026-10-27
- 触发：用户 2026-10-27 20:36 裁决「长网页肯定要分块的，用哪种都行」+「长网页分块接受你的意见」
- 关联：TODO 8.4/8.5、批次 92（点提炼口径）、P3（长文分流）

## 1. 现状与问题

`pipeline/points.py::run_points_extract` 对正文长度 > `_BODY_CAP = 6000` 的条目**一律**不抽点，
只写 `meta.points_pending_kpe` 并提示用 `tools/kpe` 分块 + `kpeimport` 导入。

真库现状（2026-10-27 20:40，正文库 55 条）：

| 正文长度 | 条数 | 现在的结局 |
|---|---|---|
| ≤ 6,000 | 29 | 正常抽点 |
| 6,001–60,000 | 16 | **0 点**（落 pending_kpe，等人手动跑 kpe） |
| > 60,000 | 10 | 同上（2.5 MB 的书也在内） |

问题：网页/文档 1–6 万字是最常见的「长文」形态（一篇长博文、一份技术报告、一章文档），
为了它们去准备本地文件跑 kpe 代价太高，于是一直停在 0 点。

## 2. 方案（不改外部工具，不动 kpe）

在 `kpoints` 管道内按段落切块，逐块跑**同一套**形态判定与抽取，合并到一个条目：

| 正文长度 | 新行为 |
|---|---|
| ≤ 6,000 | 原样单次抽取（零变化） |
| 6,001–60,000 | `_chunk_body()` 切块（≤6,000/块，优先段落 → 换行 → 句末标点 → 硬切），逐块 `point_extract.run`，点合并 |
| > 60,000 | 仍落 `points_pending_kpe`（几十块 × LLM 又贵又慢，书走离线 kpe） |

规则细节：

- **只在 LLM 可用时分块**；LLM 未启用时维持原样（照抄 6,000 字一块的点没有意义）；
- 每块沿用该条目的形态判定（`force_form` / 文学创作 split / 杂烩目录）；
- 点去重沿用现有 `point_hash` + `dl.put_point()`：逐字相同的点自动并成一条、多源挂接；
- 溯源 `char_offset` 加上块起点偏移 → 仍指向**全文**坐标，`anchor` 不变；
- 成功分块后写 `meta.points_chunked={chunks,chars,at}`，并清掉旧的 `meta.points_pending_kpe`；
- 单块（≤6,000）不写 `points_chunked`，与现状一致。

## 3. 影响面

| 项 | 变化 |
|---|---|
| 表结构 / 字段集 | 无 |
| locator scheme / `SOURCE_TYPES` / `STATUSES` | 无 |
| `CONFIG_SCHEMA_KEYS` | 无（阈值用模块常量 `_BODY_CAP` / `_CHUNK_TOTAL_MAX`） |
| CLI 参数 | 无 |
| 接口签名 | 无 |
| `meta` | 新增 `points_chunked`（只增）；`points_pending_kpe` 语义收窄为「> 60,000 字」 |
| `kpoints` 输出 | 新增 `chunked` / `chunks_total` 两个统计键（只增） |

## 4. 验证

1. 单测 `tests/test_points_chunk.py`：
   - 切块不丢字（各块拼接 == 原文）、每块 ≤ `_BODY_CAP`、优先段落边界、超长单段硬切；
   - 6,001–60,000 的条目在 fake LLM 下产出多块的点，`char_offset` 落在全文正确位置；
   - > 60,000 仍写 `points_pending_kpe`；
   - LLM 未启用时长文仍不分块（回归护栏）。
2. 真库：备份后对 16 条（6k–60k）跑 `kpoints`，人工抽查 2 条点与原文；
3. 全量 `pytest -q`（当前 679 passed / 1 skipped）+ `tests/test_canary.py` 零漂移。

## 5. 风险

| 风险 | 处置 |
|---|---|
| 跨块重复点（同句在多块出现） | `point_hash` 归并，重复只增 `points_linked`，不产重条 |
| 单块 6,000 字仍超模型窗口 | 块上限取 6,000（≈3–4k tokens），远低于现有模型窗口 |
| 分块后点变多、质量稀释 | 每块仍走自洽性闸门 `gate_point`；先只对 16 条跑，观察点数与人工抽查再决定是否放大 `_CHUNK_TOTAL_MAX` |
| 费用 | 16 条 ≈ 60 块 × 1 次调用；不重跑全库 |

## 6. 实施记录（2026-10-27 20:5x 落地）

| 项 | 计划 | 实际 |
|---|---|---|
| 分流阈值 | `_BODY_CAP` / 新增 `_CHUNK_TOTAL_MAX=60000` | 一致（模块常量，无 config 键） |
| 切块 | 段落 → 换行 → 句末标点 → 硬切 | 一致；只在窗口后 40% 找切点（`floor = start + 0.6*limit`） |
| LLM 未启用 | 未预告 | **不切块**，维持 `pending_kpe`：照抄 6,000 字/块无提炼价值 |
| 清旧标记 | 成功即清 | 一致；`_candidates` 只在 `chars > 60000` 时跳过，旧 6k–60k 标记被本轮消化 |
| 测试 | 新增切块/管道用例 | `tests/test_points_chunk.py` 7 例；`test_points.py` 4 例旧阈值改 70,000 |
| 真库 | 16 条 6k–60k | `chunked 16 / chunks 108 / points_created 383 / linked 0 / rejected 2 / pending 0`，总数 4,582 → 4,965 |

**与计划的偏差**：无（唯一新增是「LLM 未启用不切块」，已在上表登记）。

**实测观察（留给下一轮判断是否放大 `_CHUNK_TOTAL_MAX`）**：
- 单条点数与字数近似线性（52k 字 → 101 点；30.5k 字 → 14 点，切点密度取决于内容形态）；
- 溯源偏移：475 条命中 / 0 错位；580 条无偏移是「点文本为提炼、非逐字引句」的旧有成因，与分块无关；
- 跨块重复为 0（`points_linked 0`），说明 6,000 字块的边界足够正交，暂时不需要块间去重增强。
