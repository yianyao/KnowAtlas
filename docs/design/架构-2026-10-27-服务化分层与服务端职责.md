# 架构 · 服务化分层与服务端职责（2026-10-27）

> 起因（用户 2026-10-27 原话）：「我感觉这个工具以后应该会做成一个服务，提供多点多端服务，
> 仅以个人为例，几台电脑加上移动设备，不可能每台都装上这个工具，而是通过 APP 来访问。
> 所以估计还要考虑服务层、数据层、应用层的分离。」
>
> 本文是**方向性设计**，不是施工单。第一批落地动作已经发生（`serve` 内置入库巡检线程、
> `kauto` 作为无界面等价物、`datalayer/` 仍是唯一碰 SQLite 的模块），其余按阶段推进。

## 1. 一句话架构

**一个知识库实例 = 一份数据（SQLite + 正文库 + 快照）+ 一个服务进程（API + 后台任务）+
N 个只读客户端（浏览器 / 手机 / 桌面壳）。** 客户端不装工具、不碰数据库、不算语义。

```
┌───────────── 应用层（多端，无状态）─────────────┐
│  Web SPA（现有 static/）  移动浏览器/PWA  桌面壳(pywebview)  CLI(本机维护) │
└───────────────┬────────────────────────────────┘
                │ HTTPS + Bearer Token（写操作另加 X-KnowAtlas-Token）
┌───────────────▼────────────────────────────────┐
│  服务层（一个进程，有状态仅限「运行中任务」）        │
│  · FastAPI 路由（读多写少的 REST）                 │
│  · 安全中间件（Host/Origin 白名单、token、JSON-only）│
│  · 任务执行器：IngestWorker（入库巡检）/ 老化 / 备份 │
│  · 调度：周期 + 到点判定（aging.interval_hours）    │
└───────────────┬────────────────────────────────┘
                │ 只经 DataLayer 公开方法（事务 + RLock）
┌───────────────▼────────────────────────────────┐
│  数据层（唯一事实来源，单写者）                    │
│  SQLite(WAL) + content_store 正文库 + data/ 快照   │
│  + exports/ 导出产物 + config（服务端私有）         │
└────────────────────────────────────────────────┘
```

## 2. 三层边界与硬约束

| 层 | 允许做 | 禁止做 | 现有落点 |
|---|---|---|---|
| 应用层 | 渲染、筛选、发起请求、本地缓存只读数据 | 直连 SQLite、跑 LLM、抓网页、扫描本机目录 | `web/static/*`、`desktop/main.py` |
| 服务层 | 鉴权、编排 pipeline/semantic、跑后台任务、聚合统计 | 绕过 DataLayer 写库 | `web/app.py`、`web/api.py`、`web/worker.py`、`cli.py` |
| 数据层 | 表结构、事务、查询、迁移、备份 | 依赖上层（不得 import pipeline/web） | `datalayer/` |

三条不变式（写进 code review 的检查项）：

1. **`datalayer/` 是唯一 `sqlite3` 客户端**（canary 的 `grep` 纪律）；多端访问不改变这一点。
2. **语义与抓取只在服务端发生**：客户端拿到的永远是「已经算好的结论」+「可点回原文的链接」。
3. **后台任务不驻留客户端**：手机锁屏、浏览器关闭不能影响入库巡检与老化；这也是把
   `IngestWorker` 放进 `serve` 而不是放进页面的原因。

## 3. 多端形态与各自的取舍

| 端 | 形态 | 好处 | 代价 / 约束 |
|---|---|---|---|
| 桌面浏览器 | 现有 SPA，`http://<host>:8420` | 零安装、调试方便 | 需服务端常开 |
| 手机浏览器 / PWA | 同一套 SPA + manifest，加到主屏 | 不做原生也能"像 App" | 小屏需单独适配信息密度；大图/图表要懒加载 |
| 桌面壳 | `desktop/main.py`（pywebview） | 独立窗口、可离线缓存静态资源 | 仅 Windows 实测；跨平台要各自打包 |
| CLI | `kadd/ksync/kpoints/kauto…` | 批量维护、脚本化、排障 | 只装在"主控机"，不装到每台设备 |

**移动端优先级**：只读（检索、分类树、点详情、时间线）→ 轻写（收藏、标记、转正/舍弃）
→ 重写（重跑语义、导入、备份）留在桌面/CLI。

## 4. 数据层：单写者 + 网络化访问的现实选择

现状是 SQLite（WAL），优点是零运维、事务完整、备份就是拷文件；限制是**写并发单写者**。

结论：**保留 SQLite 作为唯一事实来源**，不做"多端各自一份库"。理由：

- 知识库是**个人单用户**场景，写流量极低（每天几十到几百次事务），瓶颈在 LLM 不在数据库；
- 一旦拆成"每台设备一份"，去重、分类树、点溯源、老化游标都会出现多事实来源；
- 需要远程访问时，方案是**服务端一处 + 客户端只读代理**，不是数据同步。

若未来出现多用户/协作需求，再评估 PostgreSQL（`datalayer/` 的公开方法就是迁移缝：
只要不改方法签名，SQL 方言替换不外溢）。

**网络化注意事项**（阶段 2 才需要）：

- 数据库文件与正文库**不放网盘同步目录**（WAL 在同步冲突下会损坏）；
- 备份走 `kbackup`（SQLite 在线备份 API），不要直接复制 `-wal`；
- 大字段（正文、快照）与索引表分目录，便于单独扩容与迁移。

## 5. 服务层：从"一个 serve"到"一个服务"

现在的 `serve` 已经是一个单体服务进程，服务化只需**补齐四件事**，不需要重写：

1. **后台任务**：`web/worker.py::IngestWorker`（已落地，`[ingest] enabled` 控制）。
   - 线程模型：单线程串行轮次；出错只记日志不退出；`stop()` 用 Event 唤醒式退出。
   - 为什么不用 APScheduler/Celery：单机单用户，周期 + 到点判定就够；引入队列会把
     "拷一个 db 文件就能恢复"的运维优势弄丢。
2. **任务可观测**：`task_log` + `runs` 表已记录每次巡检/老化；补一个 `GET /api/tasks`
   给页面显示"上一轮什么时候跑的、动了什么"。
3. **鉴权升级**：当前是"一次性 token 打印在启动日志 + Host/Origin 白名单"，适合
   `127.0.0.1`。远程部署前必须：反向代理终止 TLS、固定 Bearer token（`KNOWATLAS_WEB_TOKEN`）、
   关闭 `--reload`、限制来源网段。
4. **配置即服务端私有**：`config/knowatlas.toml` 与 `data/` 一样不进客户端；客户端只拿到
   API 暴露的只读视图（分类树、统计、点列表）。

## 6. 应用层：客户端只消费接口

- 现有 REST（`web/api.py`）已经是这个边界，**新增功能先问"这是接口还是页面"**：
  语义结论、老化标记、任务状态都应该有接口，页面只是渲染器。
- 客户端缓存策略：静态资源长缓存 + API `no-store`（内容会随巡检变化）；
  PWA 离线时只读最近一次成功响应的快照，不做离线写（离线写需要冲突解，收益低）。
- 移动端先做"深链"：`/points/{id}`、`/entries/{id}` 直接可分享，避免为移动端另写一套路由。

## 7. 分阶段路线

| 阶段 | 目标 | 判据 | 状态 |
|---|---|---|---|
| P0（已完成） | 单机 `serve` 全功能；后台巡检可开关 | `kauto --dry-run` 与 `serve` 巡检跑通 | ✅ 2026-10-27 |
| P1 | 局域网访问：固定 token + 手机浏览器可用 | 手机同网段打开首页、检索、点详情 | 待做 |
| P2 | 远程访问：反向代理 TLS + 只读/可写两种 token | 外网 HTTPS 打开；写操作需 token | 待做 |
| P3 | 客户端瘦身：PWA manifest + 桌面壳跨平台 | 主屏图标启动、离线只读 | 待做 |
| P4（可选） | 数据层迁移评估（PG / 全文检索外置） | 单库 > 500 MB 或检索 P95 > 300 ms | 暂不做 |

P1 的最小改动量：`[general] server_host` 放开到 `0.0.0.0`、白名单加内网段、登录页填 token
存 localStorage、HTTPS 由前置代理负责。**不要**为了局域网访问把 Host 白名单关掉。

## 8. 明确不做

- 多租户 / 账号体系 / 权限矩阵（个人知识库，token 即身份）；
- 客户端本地数据库与双向同步（见 §4，多事实来源是净损失）；
- 服务端渲染模板（现有 SPA + REST 已够，迁移成本大于收益）；
- 云端托管与对象存储（隐私优先，数据留在自己的机器上）。
