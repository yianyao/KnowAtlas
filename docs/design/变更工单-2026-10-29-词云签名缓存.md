## 1. 现状（真库实测，2026-10-29 20:4x–20:5x，serve 8420 在跑，只读）

真库规模：`entries` 368 / `points` 5,607 / `content_store` 77。

| 请求 | 实测 | 说明 |
|---|---|---|
| `GET /api/cloud?limit=60`（全库） | **2.02 / 2.06 / 2.49 s** | 72 条样本 × jieba tf-idf top8 + 点样本 ≤800 × top6 |
| `GET /api/cloud?limit=60&category_id=<文学创作>` | 0.16 s | 5 条样本 |
| `GET /api/cloud?limit=60&category_id=<人工智能>` | 0.31 s | 16 条样本 |

成本在 `web/routers/discovery.py::cloud()`：逐条 `jieba.analyse.extract_tags`，**当前没有任何缓存**——
每次切页签/切分类都全量重算。词云是「来回看」的浏览动作（R14 主题缓存的原话），同一范围重复访问必须为 0 s。

## 2. 方案

### 2.1 数据签名：`DataLayer.cloud_fingerprint()`（新增公开方法）

`datalayer/views.py`（`_ViewsMixin`）新增只读聚合方法，返回一行字符串：

```
e<entries 总数>:<MAX(exported_at)>:<SUM(LENGTH(inline_content))>:<status 分布>
:ec<entry_categories 总数>:c<categories 总数>:<SUM(LENGTH(name))>
:pt<points 总数>:<MAX(points.created_at)>:<SUM(LENGTH(points.text))>
```

覆盖的变更（即缓存失效半径）：

| 变更 | 被哪一段捕获 |
|---|---|
| 新条目入库 / 条目删除 | `entries 总数` |
| 补抓正文、清洗后正文长度变化 | `SUM(LENGTH(inline_content))` |
| 转正 / 拒绝 / 归档（`kauto`、管理页、sync） | `status 分布` |
| 分类挂接、重分类（决定词云范围与主导分类） | `entry_categories 总数` |
| 新建分类 / 改名（决定分类词元与配色槽位） | `categories 总数` + `SUM(LENGTH(name))` |
| 点重抽（kpoints：删后重插、文本变长变短） | `pt` 段（点数 / 最新 `created_at` / 文本总长） |
| 条目时间影响 `ORDER BY exported_at DESC` 取样 | `MAX(exported_at)` |

**点段为什么不复用 `points_fingerprint()`**（R14 既有）：那个指纹含 `point_vectors`
的 `COUNT/MAX(created_at)`，真库实测 **14.1 ms**（1024 维 BLOB 表），而向量重建
**不影响**词云词元——词元只吃 `points.text`。本签名只对 `points` 求 3 条聚合（6.8 ms），
失效半径更准也更便宜。两者不要合并。

**不覆盖**（由 TTL 兜底）：
- 只改 `meta.value_flag` / `link_status` / `freshness_flag` 的**少数**条目（消费面守卫读 meta，
  不进签名）——不加 `SUM(LENGTH(meta))`：真库 368 条、目标规模万级，那是 O(n) 读，会把签名成本推高；
- 点级 `aging_flag` / `meta.dupe_of` 的单行改动（决定点词元是否露面）——同理不进签名。

成本：6 条聚合，真库实测 **8–9 ms**（entries 0.9 ms + points 6.8 ms + 其余 ≈0.1 ms）。

### 2.2 缓存：`web/routers/discovery.py::/cloud`

与 R14 主题缓存同构（`web/routers/graph.py::_topics_cached`），不引入新依赖：

- 模块级常量 `_CLOUD_TTL = 300.0`、`_CLOUD_MAX = 8`；
- `register()` 内一份 `dict` + `threading.Lock`，键 =
  `库路径 | category_id | limit | cloud_fingerprint()`；
- 命中且未过 TTL → 直接返回缓存的**计算基座**（`focus` / `categories` / `words` / `sampled_entries`）；
- 未命中 → 计算 → 写入（按写入时间淘汰最旧，超 8 条开始淘汰）；
- 不做 single-flight：并发重复计算只是慢一点，等锁反而把两类请求串成一队（沿用 R14 判断）。

### 2.3 不缓存的部分：`word` facet

`word=xxx` 的分支（`cloud_facet_points` / `cloud_facet`）每次请求现算，**只缓存词元基座**：
facet 是「点某个词看它挂哪些点」，与词元聚合无关，缓存它反而要额外管失效。

实现上对缓存结果 `dict(base)` 浅拷贝后再挂 `word` / `points` / `entries`，保证缓存里的 dict 不被请求副作用污染。

## 5. 已知取舍

- 同数据同范围最多陈旧 **300 s**；数据一动（入库/补抓/转正/分类/点重抽）立即换键。
- 只改 `meta` 守卫键的少数条目、以及点级 `aging_flag`/`dupe_of` 单行改动，最多等一个 TTL（见 §2.1「不覆盖」）。
- 万级/十万级库上签名成本需实测复测（`SUM(LENGTH(inline_content))` 与 `SUM(LENGTH(text))` 是随规模增长的两项）。
- 进程内缓存 → 多 worker 部署时每个进程各一份（当前单进程 `serve`，与 R14 同前提）。
