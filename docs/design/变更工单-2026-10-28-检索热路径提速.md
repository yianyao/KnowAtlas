# 变更工单：检索热路径提速（两字 LIKE 计划修正 + 向量 cosine numpy 快路径 + 查询向量复用）

- 日期：2026-10-28
- 触发：R28 交接「下一步 ①」——本地 bge-m3 接管后语义通道恢复，但 hybrid 检索热态仍 **5.5 s**；
  用户裁决「全做：改动 1 + 2 + 3」
- 关联：R11（点聚类 numpy 快路径，`pipeline/embed_index.py::_greedy_clusters`）、
  R28（本地 bge-m3 接管）、`docs/design/变更工单-2026-10-28-检索降级与嵌入失败处理.md`（同一条
  `/api/search` 主通道，前一轮修的是「不 500」，本轮修的是「不慢」）

## 1. 现状（真库实测，2026-10-28 22:5x–23:1x，只读）

真库规模：`entries` 368 / `points` 5,607 / `content_store` 77 / `content_fts` 77。

| # | 段 | 实测 | 成因 |
|---|---|---|---|
| 1 | `_search_like` 正文段（2 字查询必走） | **1,540–1,745 ms** | 计划 = `SCAN e USING idx_entries_status` 外层 × `SCAN content_fts VIRTUAL TABLE` 内层（无 join 索引）→ 每条 active entry 重扫一遍虚表 |
| 2 | `search_fts('雪花')` 整体 | **3.0–3.4 s** | 同一病态计划（A 段 2 ms + B 段 1.5 s + 重复执行） |
| 3 | `top_similar`（5,607 × 1,024 纯 Python 余弦） | **510 ms** | 每条候选算 3 遍（query 模长、候选模长、点积），模长逐条重复 |
| 4 | `blob_to_vec` 全量（BLOB → `list[float]`） | **89 ms** | 5,607 × 1,024 个 Python float 对象 |
| 5 | 查询 encode（本地 bge-m3 短句） | **213–374 ms / 次 ×2** | hybrid 每请求 encode 两遍：`search_points_hybrid` 一次、`hybrid_search` 一次 |
| 6 | `all_point_vectors` / `search_points` / `get_point_hit` | 28 / 28 / 0.1 ms | 不是瓶颈 |

改造后同样本实测：正文段 **21 ms**（`WITH c AS MATERIALIZED`，结果集 id 逐一相同）、
`top_similar_blobs`（`np.frombuffer` 直连）**7 ms**、`top_similar`（list → 矩阵）**104 ms**。

## 2. 方案

### 2.1 `datalayer/search.py::_search_like`：正文段强制物化（无契约变化）

第二条 SQL 的派生表改 `WITH c AS MATERIALIZED (SELECT content_hash FROM content_fts WHERE text LIKE ? ESCAPE '\')`，
让 SQLite 先物化 77 行正文命中的 `content_hash` 集合，再走 `entries` 索引连接。
**只改查询计划，不改结果集**（`test_datalayer.py::test_two_char_query_finds_content` 等既有两字词用例钉住）。
`MATERIALIZED` 需要 SQLite ≥ 3.35；本机 3.53.1，pyproject 未固定 sqlite 版本，兜底见 §2.4。

### 2.2 `semantic/embed.py`：numpy 快路径 + BLOB 直连入口（无契约变化）

- `top_similar(query, candidates: dict[str, list[float]], k, threshold)`：**签名与语义不变**，
  内部加 numpy 快路径（惰性导入，`ImportError` / 维度不齐 / 空候选 → 回落现有纯 Python 实现）。
  行范数仍逐行归一，保持「完整余弦」语义，不假设调用方已归一化。
- 新增 `top_similar_blobs(query: list[float], candidates: dict[str, bytes], k, threshold)`：
  `np.frombuffer(b"".join(...))` 一次性成 float32 矩阵，省掉 `blob_to_vec` 的 89 ms 与 510 ms 余弦；
  无 numpy / 行长不齐 / 空 → 回落 `top_similar(q, {id: blob_to_vec(b)})`（保证语义一致）。
- 为什么新增而不是改 `top_similar` 的入参类型：`dict[str, list[float]]` 是既有契约
  （`tests/test_embed.py::test_top_similar_threshold_and_order` 直接钉住），
  且 `topic_recall` / `dedupe` 传的是 list；BLOB 直连只对「刚读完 BLOB 就打分的检索热路径」有意义。

### 2.3 查询向量复用（**本工单唯一动签名处**）：改动 3

- `pipeline/embed_index.py::search_points_hybrid(dl, embedder, q, *, qvec=None)`
- `pipeline/embed_index.py::hybrid_search(dl, embedder, q, limit=20, *, qvec=None)`
  —— `qvec` 缺省 `None` 时行为与现在**逐字相同**（内部自行 encode），旧调用方零改动；
  传入时不再 encode。两函数都是内部函数（无外部调用方，`grep` 确认只有 `web/routers/discovery.py`
  与测试引用）。
- `web/routers/discovery.py::search()`：`embedder` 可用时先 `encode` 一次得到 `qvec`，
  点融合与（`mode=hybrid` 时的）条目融合共用。hybrid 模式 encode **2 次 → 1 次**（省 ≈0.22 s）；
  `mode=fts` 不变（仍只用点融合那一次）。
- 边界：`qvec` 与 `q` 不一致由调用方负责（文档串写明）；encode 失败仍按
  `变更工单-2026-10-28-检索降级与嵌入失败处理` 的降级路径处理（`embed_note` + 纯 FTS）。

### 2.4 兼容性兜底

- 无 numpy（`optional` extra 未装、或用户 pip 装 core）：`top_similar` 两函数一律回落纯 Python，
  结果不变（只是慢）；`pipeline/embed_index.py` 既有 `_greedy_clusters` 的 numpy 惰性导入纪律不变。
- 老 SQLite（< 3.35）：`MATERIALIZED` 会 `OperationalError` —— 现有 `search_fts` 已用
  `except sqlite3.OperationalError: pass` 兜底到 `_search_like`，但 `_search_like` 自身没有二级兜底，
  故在 `_search_like` 内对这条 SQL 加 `try/except OperationalError` → 退回不带 `MATERIALIZED` 的原写法
  （慢但不报错）。
