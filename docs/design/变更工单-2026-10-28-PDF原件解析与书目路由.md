# 变更工单：PDF 原件解析与书目路由（KPE 通道不再吃 `book.md`）

- 日期：2026-10-28
- 触发：`docs/TODO.md` P1「KPE 实跑验收：挑一本真 PDF 走 `kauto` 的 KPE 通道…」——开工前只读排查
  发现验收路径本身走不到 PDF 原件
- 关联：工单《2026-10-27 入库即抽点与自动老化》§2.2（`ingest_router` / `kpe_runner`）、
  `tools/kpe` 的 `chunks`（PDF 目录/页码分块）

## 1. 现状（真库只读，2026-10-28 20:0x）

探针 `temp/probe_pdf_entries_20261028.py`（`mode=ro`）与单元级调用：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 真库 12 本 PDF 的 locator 全是 **`file://<文件名>.pdf`**（folder 适配器约定：根相对路径、禁绝对机器路径） | `urlsplit` → `netloc='labuladong…V2.7.pdf'`、`path=''` |
| 2 | `ingest_router._suffix()` 只取 `path` → **判不出 `.pdf`** | `_suffix('file://labuladong的算法秘籍V2.7.pdf') == ''`；`pdf_book` 分支对真数据是**死代码**，PDF 实际按字数分流（<60k 走管道） |

| 4 | 于是 PDF 走 KPE 的唯一理由（目录/页码）失效 | `book.md` 走 `window_sections` → `section_path="book"`、`page_start=0`；`kpe chunks` 直接吃原件则是 715 页 / 93 块（忠告：该 PDF 目录不可解析，也回退 `window_sections`，但其它书能吃目录） |
| 5 | 上游能力本身没问题 | `available()=True`、`_supports_max_points()=True`（`--max-points 6` 会传） |
| 6 | 只有 labuladong（469,435 字 / **0 点**）是 kauto 可达的 KPE 目标；其余 11 本已有溯源点，`_plan` 按幂等游标跳过 | `point_sources` 计数 |

## 2. 方案

### 2.1 路由（纯函数，仍零 IO）

`pipeline/ingest_router.py`：

- 新增 `_file_rel(locator)`：`unquote(netloc + path)` —— 还原 `file://` 的根相对路径；
- `_suffix()`：`path` 为空且 scheme 为 `file` 时改用它（http/https 行为不变，
  `_path()` 仍只给 `is_repo_root` 等用）。

结果：`file://书.pdf` / `file://books/书.pdf` / `file:///D:/books/书.pdf` 三种写法都返回
`kpe / pdf_book`；`.docx`、`.md` 等仍按正文长度分流。

### 2.2 源文件解析（唯一改动点）

`pipeline/kpe_runner.py`：

- `_pdf_path(cfg, locator)`（新增 `cfg` 参数）：
  1. 先取 `unquote(netloc + path)`，按 `sources.folders.roots` **逐根**试
     `Path(root) / rel` 是否存在——口径与 `fetchers/file_reader.fetch_file` 一致
     （禁盘符、禁反斜杠、禁 `..`，见 `_relative_part`）；
  2. roots 都不命中再看是否绝对 `file:///C:/x.pdf`（非 folder 来源，如手动 `kadd`）；
  3. 只有后缀为 `.pdf` 且文件存在才返回，否则 `None`（继续走 `book.md` 降级）。
- 调用点 `run_kpe_for_entry` 改成 `_pdf_path(cfg, locator)`。

不限 PDF 大小：`kpe_max_chars` 护栏仍在（正文超限直接报错，不进 dead 循环）。

### 2.3 LLM key 池（第二处缺陷，验收时才暴露）

`[llm.backends].api_key_env` 在真配置里是 **`"KNOWATLAS_LLM_API_KEY_SF1,KNOWATLAS_LLM_API_KEY_SF2"`**
（`LlmClient._keys_from_envs` 按逗号拆成 key 池）。但 `kpe_runner._llm_target()` 把整串当成单个变量名：

- `os.environ.get("A,B")` 恒为 `None` → `run_kpe_for_entry` 直接返回
  `{"status": "error", "error": "LLM 未配置（base_url/model/A,B）——KPE 无法抽取"}`
  ——**真配置下 KPE 通道一次也跑不起来**，与 `[llm] enabled` 无关；
- 上游 `kpe extract --api-key-env` 只认单个变量名，不能把逗号串透传。

修：新增 `_pick_key_env(spec)`，按 `LlmClient` 同口径拆开、取**第一个有值**的变量名；
全无值时回退第一个名字（错误信息里能看到真实变量名）。`_llm_target` 两个分支都走它。

### 2.4 预算分配（第三处缺陷：KPE 在 kauto 里排不上队）

`run_ingest_pass` 原先把预算切分放在**抓完正文之后**：

```python
# 抓取（本轮新抓到的条目随后被追加进 plan_.pipeline）
...
if budget:
    plan_.pipeline = plan_.pipeline[:budget]
    plan_.kpe = plan_.kpe[:max(0, budget - len(plan_.pipeline))]
```

于是「管道数 = 既有候选 + 本轮抓取数 ≥ budget」→ KPE 恒被切成 0。真库实测：

| 命令 | 结果 |
|---|---|
| `kauto --limit 1 --no-aging --no-activate`（20:19:30） | `fetched 1 / pipeline 1 / kpe 0`，1 秒结束 |
| `kauto --limit 6 --no-aging --no-activate`（20:20:34） | `fetched 6 / pipeline 6 / kpe 0 / points_created 11`，42 秒结束 |

只有 `--limit 0`（不限）才轮得到书 —— 即「按条数节流」与「KPE 可达」互斥。

修：把切分移到**抓取之前**，且 KPE 有候选时**先留 1 个名额**（书贵且不可分割，
不能被一堆小条目永久饿死），余量给管道。`--limit 1` 也能推到书；总work 仍以 budget 为主尺度
（抓取后顺带处理的条目属既有优化，不计入分配，注释已写明）。

### 2.5 后端 failover（第四处缺陷：KPE 单后端硬绑定）

第一次真跑（`--limit 10`，20:31–20:33）拿到 KPE 名额，但 `extract` **93/93 块全失败**、token=0、
22 秒结束：

```
failed.jsonl: LLMError: LLM HTTP 402: {"code":30001,"message":"Sorry, your account balance is insufficient"}
```

同轮管道（`LlmClient`）却正常出 76 点——因为它会在后端/ key 之间 failover，而
`kpe_runner._llm_target()` 只取**第一个**后端（硅基）就写死给子进程。

修：新增 `_llm_targets(cfg)`，按配置顺序展开 `(base_url, model, api_key_env)` 候选
（只展开「环境变量真的有值」的那些，key 池语义同 `LlmClient._keys_from_envs`）；
`run_kpe_for_entry` 逐个尝试，成功即记录 `stats["llm"]="<model>@<base_url>"`，
全失败返回最后一次错误。KPE 的 `cache/` + `--retry-failed` 保证换后端不会重复花钱。
`_llm_target()` 保留为「第一个候选」的兼容外壳。

### 2.6 产物目录绝对化（第五处缺陷：写进 git 子树）

`data_dir = Path(cfg.db_path).parent` 在 `db_path` 为相对路径（真配置就是 `data/knowledge.db`）
时得到相对目录；而 KPE 子进程的 `cwd` 是 `tools/kpe`，于是 chunks/manifest/cache 全落到
**`tools/kpe/data/kpe/<entry>/`**（git 子树里，`git status -- tools/kpe` 立刻变脏）。

修：`Path(cfg.db_path).resolve().parent`，`out` 也 `.resolve()`。首次误写产物已移到
`temp/kpe_artifacts_relative_bug/`，子树恢复干净（`git status --porcelain -- tools/kpe` 为 0 行）。

## 4. 验收

1. 定向：`uv run python -m pytest tests/test_kpe_runner.py tests/test_ingest_router.py tests/test_ingest_pass.py -q`
   （新增 3 + 1 例）；
2. 全量：`uv run python -m pytest -o addopts= -q` → 727 + 新增 / 1 skipped；`tests/test_canary.py` 零漂移；
3. 真库只读：12/12 本 PDF `plan()` 返回 `kpe/pdf_book` 且 `_pdf_path` 命中盘上原件
   （`temp/` 探针，已实测）；
4. 实跑：`kauto --limit 1` 打 labuladong（469k、0 点）→ manifest `chunk_count`、
   点 `meta.page_start`、条目 `meta.ingest = {route: kpe, chunks, points, reason: pdf_book}`。

## 5. 明确不做

- 不改 folder 适配器的 locator 约定（`file://<根相对路径>` 是「可迁移铁律」的载体，
  改绝对路径会让库换机即失效）。
- 不为「目录不可解析」的 PDF 造章节（如 labuladong 715 页、目录条 0）：那属于 KPE 上游的
  `window_sections` 策略，本仓库不动子树。
- 不放宽 `kpe_max_chars`：真库 3 本超限的书已有管道产出的点，不会进 KPE；放宽属另一次裁决。
