# 样本验证报告（2026-10-24）

> 目的：在写 97a 清洗层之前，先用真实数据把「现状到底哪里不是知识聚合」量化出来，避免凭想象设计。
> 样本：`D:\sData\KnowLedge`，31 个文件 / 208.4 MB（用户当日投放）。
> 管线：`ksync` → `ksync --fetch-limit N` → `kpoints`，全部本机实跑，无 LLM 参与。

## 3. 六处实证（对照用户需求）

### 3.1 清洗缺失：页码与目录直接进正文

| 文件 | 正行数 | 纯页码/罗马数字行 | 目录点线行 | 推广行 |
|---|---|---|---|---|
| `agentic-design-patterns-chinese` | 11,807 | **1,343（11%）** | 273（2%） | 0 |
| `agentic-ai-guide-zh-v1.1.0` | 31,958 | 769（2%） | **994（3%）** | 0 |
| `AI-Agents-in-Depth-zh-CN` | 14,506 | 314（2%） | 283（1%） | 0 |
| `Harness-Engineering` | 1,977 | 3 | 0 | **12** |
| `Obsidian-AI-v1.0.0` | 1,446 | 3 | 0 | **17** |

正文开头实况（`agentic-design-patterns-chinese`）：

```
智能体设计模式 / 构建智能系统实战指南 / AntonioGulli / ii / 目录 /
第1章：提示词链 1 / 提示词链模式概述 . . . . . . . . . . . . . . . . . 1
```

→ 用户第 2 点「只保留知识，其他都不要」**完全未达成**：封面、版权页、目录、公众号导流全在库里。

### 3.2 点层 = 文件层：无 LLM 降级时 18 个点全是「整篇 4023 字」

```
点数 18 | 全部 judge=integral | len=4023（min=max）
meta.judge_reason = "LLM 未启用：整条即点照抄保真（批次 92 提炼口径的降级路径）"
```

4023 = `inline_content` 上限 4000 + 截断标记 23 字（`…[截断，全文在 content_store]`）。也就是说：

- 一本 484,488 字的书 → **1 个知识点，且只有开头的 4023 字**（还正好是封面+目录）；
- 5.9 M 字符语料 → **18 个点**，平均每点 4023 字。

→ 用户第 3 点「以知识而非文件来组织」在**降级路径**下反向实现：点就是文件的别名。

> **重要更正（2026-10-24 18:2x）**：上述 18 点是「LLM 不可见」时的降级产物，不代表有 key 时的行为。
> 用户的 key 早已设在**用户级环境变量**里，是本 agent 进程启动早于 `setx`、读不到而误判为"未启用"。
> 从注册表导入后重跑同两篇 split 文档 → **14 个自洽知识点（92–246 字/点）**，见 §3.3 更正。
> 结论仍然成立的是：**降级路径会把点层退化成文件层**，所以 key 缺失必须当成配置故障，不能当"默认行为"。

### 3.3 无 LLM 时 split 型文档直接丢知识；有 LLM 时切点质量合格（已实测）

**无 LLM 时**：

```
ERROR 雪花写作法：split 需 LLM 切点但 llm 未启用
ERROR 雪花写作法小说家（增强版）：split 需 LLM 切点但 llm 未启用
```

规则判定这两篇需要切点（多主题），但没有 LLM 就**一点都产不出来**——不是降级，是归零。

**把用户级 key 导入进程后重跑同一命令**（`kpoints --limit 5`，73 s）：

```
integral=0 split=2 points_created=14 errors=[] pool_remaining=0
```

产出示例（每点 92–246 字，独立可读，带判定理由）：

| 来源 | 知识点（节选） | 字数 |
|---|---|---|
| 雪花写作法 | 「故事由灾难驱动：灾难=刺激=决定=新方向，安全意味着无聊……三幕式五句话段落为 ①背景+主人公 ②第一次灾难……」 | 149 |
| 雪花写作法 | 「人物立体靠价值观冲突：当珍视的东西无法兼得必须取舍时，人便挣扎……价值观→抱负→目标」 | 155 |
| 雪花写作法 | 「反派是故事的承重墙……要钻进他里头、把自己变成他，弄清他为何成为现在的样子」 | 111 |
| 增强版 | 「雪花写作法增强版给出十条实操建议：一句话概括聚焦核心冲突……」 | 223 |

→ **这正是用户裁决 1 要的形态**：带论据的观点、完整步骤，而不是"整篇 4023 字"。
→ 结论：切点能力本身够用；**缺 key 时归零必须当故障报警**，不能静默降级。

### 3.4 检索命中的是目录词

### 3.6 关系图基本是空的

### 3.7 万兴脑图：格式不支持（v14 二进制页）

```
emmx: files=1, nodes=0, degraded_files=1
meta = {"degraded": true, "reason": "page.xml 缺失或无主题节点（标题级降级）"}
```

解剖 `重要概念.emmx`（26 KB，`Document Version="14.0.3"`）：

| 内部文件 | 大小 | 内容 |
|---|---|---|
| `document.xml` | 2.7 KB | 只有 `<Properties>`（画布/DPI/作者），**无节点树** |
| `mmpage/page.bin` 等 4 个 | 2.5–21 KB | 二进制页数据；**UTF-8 明文含节点文本** |
| `theme.xml` | 35 KB | 主题样式 |

从 `page*.bin` 直接扫出的节点文本（UTF-8 明文，未压缩）：

- `page.bin`：原型、原型链、对象、函数、`基于原型链`、`函数对象是对象`、`类对象是对象`
- `page-1.bin`：作用域、执行上下文、`在运行时按序入栈`、`先进后出`、变量提升
- `page-2.bin`：闭包、`由引用环境与函数代码组成的实体即闭包`、`对象是附有行为的数据，闭包是附有数据的行为`
- `page-3.bin`：箭头函数、`this`、普通函数 vs 箭头函数的指向差异

→ 现有适配器只认旧版 `page.xml`，**这批知识（JS 原型/作用域/闭包/箭头函数，全是高质量自洽点）一条都没进来**。
好消息：文本是明文可提取，新增一个 v14 解析器是可行的（层级结构需要从二进制记录里解出）。

## 4. 结论

现状 = **文件聚合 + 噪音入库**。用户七点需求里：

| 用户要求 | 现状 | 卡在哪 |
|---|---|---|
| 1 数据源 | 30 条目 | emmx v14 不支持；微信/IMA/腾讯文档未接（阶段 B） |
| 2 只保留知识 | **未达成** | 无清洗层：页码 11%、目录 3%、推广行直入正文 |
| 3 以知识组织 | **部分达成** | LLM split 质量合格（14 点 / 92–246 字）；但 18 个点是整篇 4023 字降级，且键缺失会静默归零 |
| 4 检索聚合知识 | **未达成** | 命中目录词，返回整本开头 |
| 5 关系图聚合 | **未达成** | 1 节点 0 边 |
| 6 词云聚合 | **未达成** | 词元 = 书名/标题词 |
| 7 底线 | **未达成** | 就是第 2、4–6 点的现状 |

## 5. 据此敲定的下一步

1. **97a 清洗层必须先做**（TODO 8.1）：不是"优化"，是当前 5.9 M 字符里 11% 是页码、2–3% 是目录点线，点层吃的全是这些。
   真实误杀风险也清楚了：`Harness` 与 `Obsidian-AI` 的推广行在**结尾**，清洗要能去尾而不伤正文。
2. **点自洽性闸门（TODO 8.5）**：18 个降级点是"整篇 4023 字"，需在清洗后重跑（否则花钱在脏文本上）。
3. **emmx v14 解析（TODO 8.7）**：样本已证明文本明文可提取，值得单独立项。
4. **LLM 可用性必须显式化（本轮教训）**：key 早已配在用户级环境变量，但 agent 进程早于 `setx` 启动 → 读不到 → 静默降级成 integral。
   建议 97a 顺带把「`[llm] enabled=true` 但所有 key 环境变量为空」判成**启动 WARN + 语义层降级提示**，而不是默默产出 4023 字点。见 TODO R10。

两个必须记住的成本事实（97a 实测）：

- **单文件解析耗时**：`agentic-ai-guide` 8.4 MB / 2.68 M 字符 **87.7 s**；`AI-Agents-in-Depth` 11.1 MB **40.1 s**；
  md 文件 0.1 s。而 `Hello-Agents` **97.9 MB 用了 25 分钟**，`厦门大学…882页` 51 MB 跑 8 分钟未完被中止。
- **结论**：清洗本身不是瓶颈（20 份正文全量清洗 < 1 s），瓶颈是 pdfplumber 解析百 MB 级 PDF →
  97b 必须设"页数/字节 + 超时"闸门，超限打 degraded 并放行同步。

遗留：两个巨型 PDF 尚未重灌（库内为 0 正文）；`content_store` 有 2 行孤儿正文（被中止那轮写入、无条目引用）。

## 8. 97b 之后的 PDF 复核（2026-10-24 20:4x，11 份 PDF 全量重灌）

| 文件 | 通道 | 耗时（前 → 后） | 正文（前 → 后） | 页边删 | 通用删 |
|---|---|---|---|---|---|
| `Hello-Agents` 97.9 MB / 720 页 | pdfium | 25 分钟 → **3.29 s** | 0 → 674,468 | 6 | 96 |
| `厦大讲义` 51 MB / 882 页 | pdfium | 8 分钟未完 → **1.96 s** | 0 → 266,234 | 60 | 410 |
| `agentic-ai-guide` 8.4 MB / 599 页 | markitdown | 88 s → 54.96 s | 2,587,917（不变，重算） | — | 1,862 |
| `AI-Agents-in-Depth` 11.1 MB | markitdown | 40 s → 20.47 s | 1,045,082 | — | 632 |
| `agentic-design` 3.5 MB / 284 页 | markitdown | 37 s | 454,559 | — | 1,695 |

**页边界规则证明了什么**：厦大 882 页删掉 60 个页边页码 + 410 行跨页重复的讲义标题；正文里还剩 162 个独立数字行，
抽样看全是 `01/03` 步骤号、公式里的 `6`、`0.333`、列表 `1` —— **数据不动**，这正是"页边无条件删、正文按占比删"的分工价值。

**pdfium 的真相（否掉了自己的第一版策略）**：最初设"≤300 页且 ≤10 MB 走 markitdown"，结果 pdfium 把
`agentic-ai-guide` 的正文砍到 **30%**、`AI-Agents-in-Depth` 砍到 **43%**——行数没少多少但字符少 3 倍，
说明它把这些书的文本片段丢掉了一部分。阈值因此改成 **30 MB / 1500 页**：pdfium 只做"markitdown 跑不动"时的逃生通道。

**结论**：现在 30/30 条目都有正文（含 2 个巨型 PDF），标题级"抓不到"的窟窿清零；代价是 `content_store` 多了 6 行孤儿正文（旧版本残留）。
