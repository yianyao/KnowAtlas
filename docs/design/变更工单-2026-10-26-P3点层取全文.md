# 变更工单 · 点层正文取全文，超长条目交给 kpe（P3 收口）

## 1. 为什么

2026-10-26 19:05 核查确认：**库内 4,552 个点已经是全文分块产物**（全部 `meta.extractor=kpe`，
带 `book`/`section_path`/`quote`，溯源 `char_offset` 最远 2,477,908），点级检索也已生效。
所以「P3 重抽全库」是重复劳动，已撤销（见 `docs/log.md`）。

**剩下唯一真实缺陷在原生管道**：新同步的长文档仍会「一篇一点，只覆盖开头」——

1. `pipeline/points.py::_entry_body` 优先 `inline_content`，而
   `adapters/dbfile.py::_INLINE_CAP = 4000` 决定 inline 只是**开头 4,000 字的预览**；
2. 即便取到全文，`_BODY_CAP = 6000` 又会截断后再送 LLM。

结果是：一篇 30 万字的书会给出一条「假装覆盖全书」的 integral 点，下游 P0 分诊可能把它判成
`hard`，P1 勘误再拿它去核查事实——**污染源头**。既有 4,552 点不受影响（走的是 kpe 路径），
但任何新入条目都会中招。

## 2. 契约变更

| 项 | 变更 | 说明 |
|---|---|---|
| `points.meta` | **新增 1 键** `points_pending_kpe`（`{chars, at, why}`） | 机器后处理标记，**不进** `_SOURCE_FIELDS`；清 `null` 即删除 |
| `point_sources.char_offset` | 语义从「预览内偏移」改为「全文内偏移」 | 与既有 kpe 导入数据同口径（它们本来就是全文字符偏移）；**无数据迁移** |
| run stats | 新增 `pending_kpe`、`pending_kpe_detail`（前 20 条）、`skip_counts.pending_kpe` | run 记录是 JSON dict，无表结构变更 |
| 表结构 / `SOURCE_TYPES` / `STATUSES` / locator scheme / `CONFIG_SCHEMA_KEYS` / REST / 能力注册表 | **无** | canary 常量应零漂移 |

## 3. 实现

### 3.1 `src/knowatlas/pipeline/points.py`

**a) `_entry_body`：取较长者，而不是「优先预览」**

```python
def _entry_body(dl: Any, entry: Any) -> str:
    """条目正文：inline 预览与 content_store 全文取**较长者**（P3，2026-10-26）。

    旧口径「inline 优先」会让长文档只覆盖开头（dbfile._INLINE_CAP=4000 的预览）；
    短文档两者等价，取长者的行为等同原样。
    """
    body = (entry.inline_content or "").strip()
    if entry.content_hash:
        full = (dl.get_content(entry.content_hash) or "").strip()
        if len(full) > len(body):
            return full
    return body
```

**b) 超长正文 → 不抽点，落 `points_pending_kpe`**（主循环，紧接骨架守门之后、形态判定之前）

```python
# P3：管道单次调用吃不下（截断=假装覆盖全文）→ 交 tools/kpe 分块，宁缺勿脏。
if len(body) > _BODY_CAP:
    stats["pending_kpe"] += 1
    if len(stats["pending_kpe_detail"]) < _REJECTED_DETAIL_CAP:
        stats["pending_kpe_detail"].append(
            {"entry_id": e.id, "title": str(e.title)[:40], "chars": len(body)})
    if not dry_run:
        dl.merge_meta(e.id, {"points_pending_kpe": {
            "chars": len(body), "at": _now_iso(),
            "why": "正文超过管道单次上限，请用 tools/kpe 分块抽取后 kpeimport"}})
    continue
```

**c) `_candidates` 跳过已标记条目**（避免每轮重复读全文）

```python
if only_ids is None and not retry_blocked and e.meta.get("points_pending_kpe"):
    skipped["pending_kpe"] += 1
    continue
```

**d) 显式重抽时**：与既有 `points_gate` 清理同处只清闸门标记；
`points_pending_kpe` **不在此清**——长文只有 kpe 分块 + `kpeimport` 才真正解决，
清掉只会让下一轮重复读全文再打回标记（`--retry-blocked` 对长文等同空转，这是有意为之）。

**e) stats 初始化**：`"pending_kpe": 0, "pending_kpe_detail": []`；同时**删除** `body_truncated`
（截断路径已不存在，留着永远是 0，会误导读者以为还有截断）。

> 阈值不新造常量：沿用 `_BODY_CAP = 6000`（与 kpe 的 `target_chars=6000` 同量级）。
> 不引入 config 键，避免 `CONFIG_SCHEMA_KEYS` 变动。

### 3.2 `src/knowatlas/pipeline/kpe_import.py`

`import_kpe_dir` 里两处对齐：

1. `body` 同样改「取较长者」（现在是 inline 优先，与 3.1a 不一致会导致 `char_offset` 定位错位）；
2. 导入成功后 `dl.merge_meta(entry.id, {"points_pending_kpe": None})` —— kpe 已经解决该条目，
   标记必须消失，否则 `point_source_entry_ids` 游标与标记互相矛盾。

### 3.3 `src/knowatlas/cli.py::_cmd_kpoints`

在 GATE 提示之后追加（仅当 `pending_kpe > 0`）：

```
  PENDING 3 条正文超管道上限（meta.points_pending_kpe）：用 kpe 分块后 kpeimport 导入
           示例：uv run python -m kpe chunks <源文件> --out temp/kpe-<名>
                 uv run python -m kpe extract temp/kpe-<名> --base-url … --model …

```

## 4. 不做的事（边界）

- **不在管道内实现分块**：`tools/kpe` 已是完整实现（chunks/extract/review/stats + 断点续跑），管道再写一套就是第二套真相。
- **不改 `pipeline/aging.py` / `pipeline/errata.py` 的同名 `_entry_body`**：它们各有 `BODY_CAP`，是**送给 LLM 的上下文控制**，与点层口径无关；三处同名不同口径的收敛另案（见 §7 风险）。
- **不把 `_BODY_CAP` 提到 20k 换取「能抽完」**：长文一篇一点本身就不是想要的知识粒度（TODO P3 原话「把章节名变成知识点」），提高上限只是把「假装覆盖 8%」改成「假装覆盖 60%」。
- **不重抽既有 4,552 点**（已核查是全文产物）；不改 `data/eol.json`、不动 EOL 语义。
- **不新增 REST 接口**：`points_pending_kpe` 先只进 CLI 报告与 meta，UI 呈现等有真实条目再议。

## 7. 风险与已知取舍

1. **新长文档不再立刻有点**：这是有意的——它会有 `points_pending_kpe` 与 CLI 提示，用户跑 kpe 后自动消失。若用户嫌麻烦，可另议「管道内直接调度 kpe」（大件，不在本批）。
2. **`_candidates` 与主循环各读一次全文**：30 条目量级可忽略（×2 次 content_store 读）；条目上千时再上缓存。
3. **`--retry-blocked` 对长文等同空转**：它会绕过候选过滤，但主循环仍转 kpe 并打回标记
   ——刻意如此，避免「重试」把截断抽点又放回来。真正的解除路径只有 `kpeimport`。
   （若将来要支持「正文已变短想改走管道」，加一个显式 `--clear-pending` 即可，不塞进 retry。）
4. **三处同名 `_entry_body`**：本次只改点层，aging/errata 仍看预览。它们核查的是「条目是否该判时效/是否有错」，语义是条目级，暂不影响；收敛另立工单。
5. **骨架守门输入变长**：`is_skeleton_body` 现在看全文而非 4,000 字预览，可能对少数条目改判——方向更正确（骨架判断需要全局），但属于行为变化，单测需覆盖短文档不回归。
