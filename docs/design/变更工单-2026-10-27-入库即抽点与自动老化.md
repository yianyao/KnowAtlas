## 2. 方案

### 2.1 新增配置键（`CONFIG_SCHEMA_KEYS` 变更 → canary 需同步）

```toml
[ingest]                     # 入库即处理（worker / kauto 共用）
enabled              = true  # serve 内置 worker 开关
interval_seconds     = 600   # 巡检周期
max_entries_per_run  = 10    # 每轮总条数上限（费用护栏）
max_retries          = 2     # 单条目失败重试上限（超限进 meta.ingest.dead）
allow_kpe            = true  # 允许自动走 KPE（书/超大文档）
kpe_max_chars        = 600000  # 单本进 KPE 的正文字数上限（防 250 万字级误入）

[points]                     # 抽点阈值（KPE 与管道同源）
max_per_chunk        = 6     # 单块/单条最多几个点（KPE --max-points；管道 split 上限）
chunk_chars          = 6000  # 管道分块目标字数
chunk_total_max      = 60000 # 管道内分块上限；超过改走 KPE

[aging]
auto                 = true  # worker 周期跑老化
interval_hours       = 24
limit_per_run        = 200
# 域闸门：这些一级分类（含子树）下的点**不自动老化**——社科/人文类没有「技术过时」概念。
exclude_categories   = ["文学创作", "哲学", "历史", "文学", "艺术", "社会学", "心理学",
                        "经济学", "政治学", "法律", "教育", "宗教", "人类学", "语言学", "传播学"]
```

`_TOP_SECTIONS` 同步加 `ingest` / `points` / `aging`（环境变量覆盖识别用）。

### 2.2 新模块

| 文件 | 职责 |
|---|---|
| `pipeline/ingest_router.py` | 纯函数 `plan(entry, body_chars, cfg)`：按 locator scheme/扩展名/正文规模/主机判「走哪个工具」——`pipeline` / `pipeline_chunked` / `kpe` / `skip(needs_capability|repo_page|not_knowledge|too_large)` |
| `pipeline/ingest.py` | `run_ingest_pass(cfg, dl, semantics, ...)`：①pending 激活（L0 守门）②补抓正文 ③按路由抽点（管道 or KPE）④审计与护栏；`activate_pending()` 可单独调用 |
| `pipeline/kpe_runner.py` | 以 `sys.executable -m kpe`（`PYTHONPATH=tools/kpe`）跑 chunks+extract，再走既有 `kpe_import.import_kpe_dir` 入库（**不 import tools/kpe**，与适配器纪律一致，只借 CLI） |
| `web/worker.py` | `IngestWorker`（Thread + Event）：周期跑 `run_ingest_pass`；老化按 `aging.interval_hours` 独立节拍 |

### 2.3 行为变更

1. **`new_entries` 第三取值 `"auto"`**：新条目先过 L0 守门（`judge_value` + `is_index_page` +
   `is_garbled`）——命中 → `rejected`（`task_log.action=auto_reject`，reason 落 `value_flag_reason`）；
   未命中 → **自动转正 active**（`task_log.action=auto_activate`）。缺省仍是 `"active"`/`"pending"`，
   零行为变化。历史 pending 用 `kauto --activate-only` 一次性回填（先 `--dry-run`）。
2. **`ksync` 尾部自动抽点**：`[sync] auto_points`（沿用仓库既有 `[sources.*]` 之外的新顶层节？
   否——**不加 `[sync]` 节**，由 worker 承担，`ksync` 不被拖慢）。`ksync` 行为不变。
3. **`kauto` 新命令**：`kauto [--dry-run] [--limit N] [--activate-only] [--no-aging]`——
   worker 的无界面等价物，供计划任务/无 serve 场景。
4. **抽点阈值参数化**：`point_extract.run` 接受 `item["max_points"]`（缺省 8，`points.max_per_chunk`
   覆盖）；`pipeline/points.py` 的分块上限/目标字数读 `[points]`。
5. **老化域闸门**：`run_lifecycle` 与 `run_point_aging` 的候选都追加「点所属条目的一级分类 ∉
   `aging.exclude_categories`」；点级隔离保持（`set_point_aging` 只改单行，永不改条目状态），
   补回归测试钉死。
6. **自动老化**：worker 每 `aging.interval_hours` 跑 `run_lifecycle`（版本型零 LLM 先行），
   `limit_per_run` 限流；`kaging` 命令行为不变。

### 2.4 KPE 参数（上游改动）

`tools/kpe` 是独立仓库子树（`D:\kpe`）：`extract` 新增 `--max-points`（缺省 6），
`prompt.build_system(n)` 生成「1–N 个知识点」。本仓库不直改子树，改上游后
`git subtree pull --prefix=tools/kpe kpe main --squash` 拉回。

## 4. 验证

1. 单测：`test_ingest_router.py`（8 类路由）、`test_ingest_pass.py`（激活/抓取/抽点/护栏）、
   `test_aging_domain_gate.py`（文学创作 hard 点不候选）、`test_aging_isolation.py`
   （老化 A 点不动 B 点、不动条目状态）、`test_points_threshold.py`（max_per_chunk 生效）。
2. 空库端到端：`kinit` → 配一个新源 → **只跑一次 `ksync`** → `kauto --once` → 断言
   该源全部 active 条目有 `content_hash` 且点数 > 0，`task_log` 能回答每条「抓了没/抽了没/为什么没」。
3. 真库：`kauto --activate-only --dry-run` 看 132 条回填清单；`kauto --dry-run --limit 5` 看路由；
   实跑后 points 只增不减。
4. 全量 `pytest -o addopts= -q`（基线 694 passed / 1 skipped）+ `tests/test_canary.py` 零漂移。

## 5. 风险与处置

| 风险 | 处置 |
|---|---|
| 自动转正误放噪音（首页/列表页） | 先过 L0 守门；误判可在管理页一键 `rejected`；`auto_activate` 有 `task_log` 可回滚 |
| 费用失控 | 每轮条数上限 + 重试上限 + `dead` 队列 + `dry-run` 报告；KPE 单本字数上限 |
| KPE 子进程失败（缺 pdfplumber / 网络） | 失败落 `meta.ingest.reason`，不进 `dead`；下一轮重试，超限后停 |
| 老化误杀人文内容 | 分类黑名单 + `kind=hard` 双闸门；只标 `stale` 不删；`ok` 免疫 |
| worker 与 CLI 并发写库 | 同一 SQLite WAL + `DataLayer._lock`；worker 每轮单线程，不与 `ksync` 同时跑（serve 内串行） |
