# 变更工单 · R11 知识主题端点：numpy 快路径 + top-N 截断

## 1. 为什么

8.6 三视图验收（2026-10-26 22:20）实测：`/api/graph/topics` 在真库规模下 **378.7 s** 才返回，
前端 `graph.html` 点「知识主题」按钮即卡 6 分钟；返回 **1,003 个主题、平均 2.4 点/簇**，
画出来也读不了。TODO 注释里「真库 ~114 点、贪心 O(n²) 毫秒级」的假设已过时。

`temp/probe_r11.py`（只读，抽样 800/1,600 点 + 二次外推）的拆解：

| 热点 | 实测 | 全量占比 |
|---|---|---|
| `embed_index._greedy_clusters` 纯 Python 双循环 | 800 点 21.0 s / 1,600 点 76.0 s | **~340 s（九成）** |
| `graph_topics._topic_name` → `keywords.shared_words` | 29 ms/主题 × 1,003 | ≈ 29 s |
| `graph_topics._all_point_hits` 逐点 `get_point_hit` | 0.07 ms/点 | ≈ 0.3 s —— 原 TODO 猜的热点**不成立** |

即：真正贵的是「每加入一个点都要跟全部簇心做 1,024 维点积」的纯 Python 外循环，
取点与命名都是次要项；「批量取点」这一原本设想的优化项无需做。

numpy 对照实测（同一份真库向量，同阈值 0.72）：800 点 **0.067 s**、1,600 点 **0.188 s**，
外推全量 **≈ 1.5 s**；且两档样本的**簇划分与纯 Python 完全一致**（`same_as_pure = true`）。

## 2. 契约变更

| 项 | 变更 | 兼容性 |
|---|---|---|
| `GET /api/graph/topics` | 新增**可选**查询参数 `limit`（整数，默认 80；≤0 或 >500 由服务端夹到 `[1, 500]`） | 不传即默认 80，老调用方零改动 |
| 响应字段 | **新增** `total`（主题总数）、`limit`（生效上限）、`truncated`（是否被截断）；`topics` / `singles` / `vectors` / `threshold` 语义不变 | 纯新增字段，前端按需读；旧前端不读也不报错 |
| `pipeline/graph_topics.py::topic_clusters` | 签名加 `limit: int | None = 80`（`None`/`0` = 不截断，返回全部） | 内部函数，仅 api.py 与测试调用 |
| `pipeline/embed_index.py::_greedy_clusters` | 内部实现换 numpy 向量化；保留纯 Python 兜底（numpy 缺失 / 维度不一致 / 点数 < 64 时） | **不改签名、不改返回形状**，簇序与簇内序仍 = 输入序 |
| `pyproject.toml` | `dependencies` 显式加 `numpy`（原本只从 `pandas` 传递获得，不该靠传递依赖） | 打包面，无契约影响 |
| 表结构 / 字段 / locator scheme / `SOURCE_TYPES` / `STATUSES` / `CONFIG_SCHEMA_KEYS` / 能力注册表 | **无** | canary 六项零漂移 |

## 3. 数值等价口径（为什么敢换实现）

1. **同一套贪心语义**：按输入序逐点，与已有簇心（成员均值）算余弦相似度，≥ 阈值归入最高者，
   否则自立新簇；簇心增量更新公式 `(x·(n-1)+y)/n` 逐元素一致。
2. **精度**：矩阵与簇心一律 `float64`（与 Python float 同宽）。点积由 BLAS 求和（可能重排加法），
   与纯 Python `sum()` 存在 ≤1 ulp 差异——只有当某个相似度**恰好压在 0.72 上**才可能翻转归属；
   真库 800/1,600 点实测两档**簇划分完全相同**。
3. **兜底不丢**：`import numpy` 失败、向量维度不一致（多模型混排）、点数 < 64 时走原纯 Python 路径，
   行为与今日完全一致——不把新依赖变成硬故障面。
4. **回归测试**锁住等价性：随机 300×64 维向量的簇划分必须与纯 Python 逐簇相同
   （`tests/test_graph_topics.py::test_greedy_clusters_numpy_matches_pure`）。

## 5. 不做什么

- **不做 P1 进程内 TTL 缓存**：本轮目标是「点一次 4 s 内出图」；缓存要跟点向量批次变化挂钩，
  多一层失效状态，等真正出现「反复点」的诉求再加。
- **不调阈值 0.72**：阈值是 56/60/88 三批统一口径，改它等于改主题语义，属产品裁决，不在本单。
- **不改主题命名口径**（共享词、禁发明）：只改「对几个主题算名字」，不改「怎么算名字」。
- **不把 4,552 点全画出来**：top-N 本来就是产品诉求（1,003 个 2.4 点小簇不可读）。

## 7. 已知限制

- BLAS 点积与纯 Python 求和在 0.72 边界处可能有 ulp 级翻转（真库实测无差异）；如未来出现「同库两次聚类结果不同」，先查向量是否被并发重写，再查阈值贴边。
- `limit` 上限 500 是防呆：再大就退化成今天的 378 s 体验（不阻断，但也不保证前端可读）。
- 主题数 1,003 本身是阈值产物，`total` 若长期远大于 `limit`，说明阈值口径该复核（另案例）。
