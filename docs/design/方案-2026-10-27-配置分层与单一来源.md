# 方案 · 配置分层与单一来源（2026-10-27）

> 起因（用户 2026-10-27）：「日后往服务层、数据层、应用层拆分。那很多参数、配置之类的，
> 是否应该定义各种配置文件，而不是乱七八糟啥都有？」
>
> 结论先说：**不要按"层"拆成多个配置文件**——那会制造"哪份生效"的新问题。
> 要做的是**把 59 个键按"谁拥有 / 能不能调"分成四类**，配一个"生效值 + 来源"视图，
> 再加一份自动生成的配置参考。这样它乱不乱一眼可查，而不是靠多几个文件解决。

## 1. 现状（59 个键，1 个文件）

| 段 | 键数 | 典型键 |
|---|---|---|
| `[general]` | 10 | `db_path` `content_root` `backup_*` `server_host/port` `log_level` |
| `[web]` | 1 | `token_env` |
| `[llm]` | 7 | `enabled` `model` `base_url` `api_key_env` `backends` `max_batch` `temperature` |
| `[embedding]` | 3 | `enabled` `provider` `model_path` |
| `[fetch]` | 11 | `on_sync` `max_fetch_per_run` `rate_limit_qps` `timeout_seconds` `pdf_backend` `deepseek_*` |
| `[clean]` | 3 | `enabled` `redact_enabled` `min_keep_ratio` |
| `[aging]` | 4 | `auto` `interval_hours` `limit_per_run` `exclude_categories` |
| `[ingest]` | 6 | `enabled` `interval_seconds` `max_entries_per_run` `max_retries` `allow_kpe` `kpe_max_chars` |
| `[points]` | 3 | `max_per_chunk` `chunk_chars` `chunk_total_max` |
| `[sources.*]` | 12 | 每源一段（`folders`/`bookmarks`/`emmx`/`manual`/`mail`/`db`/`session`/`opml`/`bilibili`/`wx`/`ima`/`txdoc`） |

加载规则（已实现）：代码默认值 → `config/knowatlas.toml` → `KNOWATLAS_<SECTION>_<KEY>`
环境变量覆盖；秘密（key/token）只从环境变量读，配置文件里只写 `*_env` 变量名。

真实问题不在键多，而在三件事：

1. **层归属不清**：`db_path` 是数据层的，`server_port` 是服务层的，`llm.model` 是语义层的，
   但它们在同一个文件里、同一个类上，看不出"客户端该不该知道"。
2. **有些"参数"根本不在配置里**：清洗阈值、自洽性闸门阈值、`AGING_BATCH` 这类散在代码常量里，
   没有"哪些能调、为什么不开放"的说明。
3. **没有生效视图**：改了 env、改了 toml，最终哪个值生效、来自哪里，只能人肉推。

## 2. 决策：四类旋钮（不是四个文件）

| 类 | 名字 | 判据 | 放哪 | 谁能改 | 例子 |
|---|---|---|---|---|---|
| D | **部署参数** | 换一台机器就要变 | 配置文件 | 运维/用户 | `db_path` `content_root` `server_host` `server_port` `backup_dir` `log_level` |
| S | **秘密** | 泄露即事故 | **只放环境变量** | 用户 | LLM key、DeepSeek fetch key、`KNOWATLAS_WEB_TOKEN`、bilibili sessdata |
| T | **领域阈值** | 同一份数据、不同取舍 | 配置文件（有默认+上下界） | 用户 | `points.*` `aging.*` `ingest.*` `fetch.max_fetch_per_run` `clean.min_keep_ratio` |
| I | **实现常量** | 改了会破坏判据自洽 | **代码常量，不开放** | 只有开发者（走工单） | 清洗的页码占比/目录点线/重复行阈值、闸门阈值、EOL 表 |

**I 类不是遗漏，是设计**。清洗阈值（页码占比 2%、目录点线 3 条…）是从 5.9 M 字符真实语料量出来的，
放成配置键只会让人把它调成"洗不干净"；闸门阈值同理——它定义"什么算一个合格知识点"，
可调就等于"什么都能过"。这条理由要写进 `config/knowatlas.example.toml` 的注释里（已部分写了）。

## 3. 文件布局：一份生效 + 一份模板

```
config/
├── knowatlas.example.toml   # 模板（进仓库）：全键 + 注释 + 默认值 + 分节说明
├── knowatlas.toml           # 本机生效（gitignore）
├── knowatlas.home.toml      # 可选：家用服务器那一份（gitignore）
└── knowatlas.server.toml    # 可选：远程部署那一份（gitignore）
```

- **同一时刻只有一个生效文件**，靠 `KNOWATLAS_CONFIG` 指定绝对路径；
  不指定时按现有规则找 `config/knowatlas.toml`。
- **不做多文件 merge/inherit**（TOML 没有标准 include，自己实现 merge 会引入"哪层覆盖哪层"
  的调试地狱）。多环境 = 多个完整文件 + 一个环境变量切换。
- `KNOWATLAS_CONFIG` 是**环境变量**，不进 `CONFIG_SCHEMA_KEYS`（不是配置文件键），
  但它改变加载行为 → 实施时要走一张小工单 + canary 不动 + 一条测试（`test_config_path_env.py`）。

优先顺序（固定，写进文档）：

```
代码默认值  <  config 文件  <  环境变量 KNOWATLAS_<SECTION>_<KEY>  <  秘密类只能是环境变量
```

（秘密类没有"默认值"这一层：缺了就报错或用能力降级，绝不内置。）

## 4. 层归属：谁读哪一段

| 层 | 读哪些段 | 不该读 | 理由 |
|---|---|---|---|
| 数据层（`datalayer/`） | 只 `[general]` 的 `db_path` / `content_root` / `backup_dir` | llm/fetch/points/aging | 数据层不知道"知识怎么抽" |
| 服务层（pipeline/semantic/web 服务端） | 全部 | — | 它负责编排 |
| 应用层（浏览器/桌面壳/PWA） | **零配置** | 全部 | 只从服务端拿 `baseUrl` + token（登录页填），不读 TOML、不读 env |

这条直接回答"服务化后配置放哪"：**配置全在服务端**，客户端只有"连哪个地址 + 用哪个 token"。
手机装个 PWA 不需要知道 `db_path` 在哪，也不该知道。

## 5. 可观测性：`kconfig` 子命令 + 自动生成的参考

新增一个 CLI（属工单范围，不是本文就能改）：

```
kconfig show [--json] [--diff-defaults]   # 打印生效值 + 每项的来源（default/file/env）
kconfig check                             # 未知键、类型错、越界、secret 写进文件
kconfig docs --out docs/参考-配置.md       # 从 schema + 默认值 + example 注释生成参考
```

`show` 的输出形态（示例）：

```
[points] max_per_chunk = 6        ← file
[points] chunk_chars   = 6000     ← default
[llm]    model         = deepseek-v4.1-flash-1017  ← file
[llm]    api_key_env   = KNOWATLAS_LLM_API_KEY     ← file (secret: 未读取)
```

生成参考文档的规则（借 `pg/tools/gen_docs.py` 的思路，不引入其仓库，见 ADR §6）：

- 键集必须等于 `CONFIG_SCHEMA_KEYS`（CI/测试断言，防 example 与代码漂移）；
- 每个键必须有：类型、默认值、单位、取值边界、`D/S/T/I` 分类、"改它会发生什么"一句话；
- `I` 类不出现在参考里（只出现在 ADR 的理由段）。

这一条解决"乱七八糟"的**可见性**问题：不用打开 5 个文件，`kconfig show` 一眼看清。

## 6. 迁移步骤（按收益排序）

| 步 | 内容 | 是否改契约 | 工时 |
|---|---|---|---|
| 1 | 落地四类标注（`config.py` 每个 property 加 `# D/S/T`；example.toml 分节注释） | 否（纯注释） | 0.5 天 |
| 2 | `kconfig check` + 键集一致性测试（example vs schema） | 否（新命令） | 0.5 天 |
| 3 | `kconfig show --effective`（值 + 来源） | 否 | 0.5 天 |
| 4 | `KNOWATLAS_CONFIG` 支持 + 多环境示例注释 | **是**（小工单） | 0.5 天 |
| 5 | `kconfig docs` 生成 `docs/参考-配置.md` | 否 | 0.5 天 |
| 6 | 常量收编：`AGING_BATCH`、`BODY_CAP` 等逐步进 `[aging]/[points]`（**只收有真实调整需求的**） | 是（每键一张小工单） | 按需 |

第 6 步不要一次做完：常量集中本身有价值（"改口径只改一处"），但把每个常量都暴露成配置是反模式
（见 §7）。只收"用户真的会调"的，其余留在代码里、在 ADR 里说明理由。

## 7. 反模式（明确禁止）

| 反模式 | 为什么禁止 |
|---|---|
| 按层拆 3 个 TOML（`data.toml` / `service.toml` / `app.toml`） | 层之间要共享键（如 `db_path`），拆开后要么重复要么互相引用，调试时不知道哪份生效 |
| 配置文件里写密钥 | 会被提交、会被备份、会出现在 `kconfig show` |
| 把清洗/闸门阈值开放成键 | 会让"洗不干净"和"什么点都能过"变成可配置 |
| 客户端读配置文件 | 客户端不该知道服务端路径与模型；只拿 baseUrl + token |
| 用环境变量传结构化数据（列表/字典） | `_apply_env_overrides` 只支持标量；结构化数据放文件 |
| 每个源一个配置文件 | 源是"一段"，不是"一份"；`[sources.*]` 已经隔离得很好 |
