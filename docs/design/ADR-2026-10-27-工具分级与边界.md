# ADR-2026-10-27 · 工具分级与边界（Tier A / B / C）

- 状态：**已采纳**（用户 2026-10-27 裁决）
- 决策者：用户 + Agent
- 相关：`docs/模块地图.md`、`方案-2026-10-27-四个大文件拆分.md`、
  `架构-2026-10-27-服务化分层与服务端职责.md`

## 1. 背景

过去三天里，"工具"长出了三种形态：独立仓库（`kpe`）、外部独立工具 + 薄封装（`session-guard`）、
仓库内模块（`clean`/`eol`/`embed`…）。用户的原话是：「现在感觉好乱，就是脚本调脚本」。

真实痛点不是**目录**，是**调用方式混用**：同一个能力可能被 import、被 `subprocess`、
被 `tools/*.py` 桥接层三种方式之一调用，读代码时无法预期"改这里会不会影响那里"。

本 ADR 把"要不要独立"从直觉变成判据，并把调用方式固定下来。

## 2. 判据：什么才值得独立成仓库

同时满足 **≥3 条**才进 Tier A：

| # | 判据 | 反面（不满足就别独立） |
|---|---|---|
| C1 | **有独立消费者**：脱离 KnowAtlas 的库/配置也能用 | 只能给主库用（如 `domain_gate` 要读 `entries` 表） |
| C2 | **依赖重/可选/平台相关**：不该拖累主安装 | 只用标准库 + 主库已有依赖 |
| C3 | **边界是文件/HTTP**：输入输出不是 Python 对象 | 入参是 `Entry`/`Point`、出参是 `DataLayer` 调用 |
| C4 | **有独立版本语义**：别人会 pin 版本、看 CHANGELOG | 跟着主库一起发版 |
| C5 | **可离线单测**：零 DB、零主配置、零网络 | 测试必须造库/配 key |

补充否决项（命中任一 → 不独立）：需要与主库同事务、需要主库的 ORM 模型、需要与主库
同时改才不破。

## 3. 三层定义

### Tier A · 独立仓库（vendor 或安装）

| 项 | 内容 |
|---|---|
| 职责 | 一整个可独立交付的能力；有自己的 README/CHANGELOG/版本/测试 |
| 允许 | 只依赖标准库或自己声明的依赖；通过**文件**或**子进程**与主库交互 |
| 禁止 | import 主库任何模块；读主库配置/数据库；假设主库目录结构 |
| 目录 | 主库内只出现在 `tools/<name>/`（subtree）或 `tools/<name>.py`（桥接） |
| 测试 | 自己的测试套件，离线可跑；主库不为它写业务测试 |
| 现在有 | `kpe`（subtree，v0.2.0）、`session-guard`（外部安装，`tools/*.py` 是桥接） |

### Tier B · 内部包（可拔，但共享主库）

| 项 | 内容 |
|---|---|
| 职责 | 领域算法/规则，天然可独立但当前只服务主库 |
| 允许 | import `models`/`errors`/`ids`；被 `pipeline` 调用；纯函数优先 |
| 禁止 | 被更底层（`datalayer`）反向 import；在 `__init__` 暴露不稳定内部符号 |
| 目录 | 保持现有位置，但必须是**单一入口**：`from knowatlas.pipeline.clean import clean_text` |
| 测试 | 独立测试文件，尽量零 IO；需要库的用 `dl` fixture |
| 现在有 | `pipeline/clean.py`、`semantic/eol.py`、`semantic/embed.py`、`pipeline/point_gate.py`、`pipeline/domain_gate.py`、`pipeline/export.py`、`pipeline/kpe_import.py` |

Tier B 的意义：**先长成"可拔"的形状**（单一入口、零反向依赖、能离线测），哪天满足 C1/C4
再抽出去，不用改调用方。

### Tier C · 核心（不独立、不允许被绕过）

| 项 | 内容 |
|---|---|
| 职责 | 契约与事实来源：表结构、模型、ID、错误、配置、编排 |
| 允许 | 被所有层 import |
| 禁止 | 依赖任何具体工具；出现 `subprocess`/网络/LLM 调用 |
| 目录 | `datalayer/`、`models.py`、`ids.py`、`errors.py`、`config.py`、`registry/`、`pipeline/` 编排层 |
| 测试 | 全量回归 + canary；任何契约变更先写工单 |

## 4. 调用方式规范（治"脚本调脚本"）

| 场景 | 唯一允许的方式 | 反面教材 |
|---|---|---|
| 主库内部能力（Tier B/C） | 直接 `import` | 为了"解耦"去 `subprocess` 调自己人 |
| Tier A 重工具（kpe） | `subprocess` + **版本契约**：启动前 `--version` 探测、能力不支持就降级、失败码写进 `meta` | `import kpe` 或 `sys.path.append` 后 import |
| Tier A 轻工具（session-guard） | `tools/<name>.py` 桥接：只做参数转译与路径解析，≤200 行 | 把工具逻辑复制进主库 |
| 跨进程数据 | 文件（JSON/JSONL）+ 目录约定 | 共享 SQLite 连接/临时环境变量传对象 |

明确一点：**`subprocess` 不是脏**。tier A 的"文件进文件出"工具用子进程是正确边界；
脏的是"同一层内两种调用方式并存"。所以规范是：**按层定方式，不按心情定方式**。

## 5. 新增/升级一个 Tier A 工具的流程

新增：

1. 先过 §2 的判据（≥3 条），把结论写进 `docs/design/变更工单-*.md` 或本 ADR 的附录。
2. 新仓库（README/CHANGELOG/LICENSE/测试），主库只加 `tools/<name>/`（subtree）或桥接文件。
3. 主库侧写**适配器**：`pipeline/<name>_runner.py` 或 `<name>_import.py`，只碰文件格式，
   不 import 工具；工具缺失时必须降级而不是崩。
4. 加一条测试：工具不可用时主链路仍绿（用"假工具目录"模拟）。

升级（三种方式，按形态选，不混用）：

| 形态 | 升级方式 | 例子 |
|---|---|---|
| subtree | `git subtree pull --prefix=tools/kpe kpe main --squash` | kpe |
| 外部包 | `pip install -U` / `uv tool upgrade`；`tools/*.py` 只解析版本 | session-guard |
| 拷贝骨架 | `bootstrap.py` / `upgrade_spec.py`（core 区替换，本地区保留） | pg（见 §6） |

## 6. 案例：`pg`（项目规范母版）为什么**不** vendor 进来

`pg`（<https://github.com/yianyao/pg>）是**规范母版**：`AGENTS.md` 规则本体、`bootstrap.py`
生成项目骨架、`tools/{check,gen_docs,guard,handoff,audit_rules,upgrade_spec}.py`、`template/`。

按 §2 判据打分：C1 ✅（任何项目都能用）、C2 ✅（纯标准库）、C3 ❌（产物是**文件**，
不是运行时接口）、C4 ✅（有 `SPEC_VERSION` 与版本化升级）、C5 ✅（自带 unittest）。
表面上看满足 4 条，**但 C3 不满足**——它不是"被调用的工具"，而是"被复制的规范"。

更关键的是它的设计契约：

- `bootstrap` 把文件**复制**进项目根，已存在的文件绝不覆盖；
- `SPEC_VERSION` 记录"项目用的规范版本"，**故意不自动更新**："项目里的规则要经过一次评审再改，
  不能半夜自己变"；
- `upgrade_spec --tools` 才覆盖脚本，`AGENTS.md` 的本地规则区（`local:begin/end`）永远保留。

如果像 kpe 一样 subtree 进 KnowAtlas：

1. 会出现**两套 `AGENTS.md`**（subtree 的 core 区 vs 本仓库已有的规则），谁生效说不清；
2. `tools/` 直接撞车：pg 的 `guard.py` 要接管 `session_*`，而 KnowAtlas 已有 4 个桥接薄封装
   和一个运行中的计划任务；
3. 绕过 `upgrade_spec` 的"评审后升级"，等于把"规则不能自己变"这条设计前提废掉。

**结论**：不 vendor。可选的三条接入路径，按收益排序：

| 选项 | 做法 | 成本 | 建议 |
|---|---|---|---|
| ① 只借"生成文档" | 把 `gen_docs.py` 的生成配置参考思路搬进主库（见配置分层方案），不引入仓库 | 半天 | **推荐** |
| ② 借 `guard.py` 入口 | 用它替换 `tools/session_check.py` 等 4 个薄脚本 + 计划任务接线（复制单文件 + 本地裁剪） | 半天 | 可选 |
| ③ 正式接入母版 | 对 KnowAtlas 跑 `bootstrap.py` 只补缺失文件 → 评审合并 `AGENTS.md` core 区 → 写 `SPEC_VERSION` | 1–2 天 + 评审 | 若决定"以后所有项目统一规范"再做 |

无论选哪条，`pg` 都保持在 `D:\sData\git\pg` 独立维护（已同步到 `bf34cf7`），不进入主仓库。

## 7. 后果

正面：

- "要不要独立"有判据，不再靠感觉；新工具先问 5 个问题。
- 调用方式按层固定，读代码能预期边界；`subprocess` 只出现在 Tier A 适配器。
- Tier B 保持"可拔"形状，未来抽取不用改调用方。

负面/代价：

- Tier B 的"单一入口"需要纪律，code review 要盯 `__init__` 暴露面。
- 子进程方式需要版本探测与降级路径（`kpe_runner._supports_max_points` 是模板）。
- 多一层规范文档要维护（本 ADR 即为源头，变更走工单）。

## 8. 复查触发条件

出现以下任一情况时重开本 ADR：

- Tier B 中某个模块被第二个项目复用（→ 升 A）；
- 某个 Tier A 工具开始需要读主库数据（→ 边界破了，要么回到 B，要么改成 HTTP 服务）；
- 主库要跨平台分发（→ 重新评估"外部包 vs subtree"）；
- `tools/` 里桥接文件超过 200 行（→ 说明工具该被正式抽象，而不是继续桥接）。
