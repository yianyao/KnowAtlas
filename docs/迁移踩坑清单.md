# 迁移踩坑清单（换机必读）

配套：SOP §9（迁移到新机器的六步操作）。本文回答的是"步骤背后的坑"——全部是
2026-10-19/20 两天的真实踩坑记录，换新机器、重装环境、新人接手时**先通读本文**。

## 一、依赖坑（最高频，用户点名案例）

### 1. markitdown 裸装 = Office 文档解析全废

- **现象**（2026-10-20 案例）：`pip install markitdown` 后库内 489 条 Office 条目
  （docx/xlsx/xls/pptx/doc/ppt）全部报 `MissingDependencyException`，被打
  unparseable 进待清理候选——文件本身全是好的。
- **根因**：markitdown 的各格式转换器（mammoth=docx、openpyxl+pandas=xlsx、
  xlrd=xls、python-pptx=pptx）都是**可选依赖，裸装一概没有**。
- **已修**：五个依赖已写入 requirements-core.txt 与 pyproject.toml（两处必须同步，
  uv 只读 pyproject）。新机装依赖后**必须拿真实 docx/xlsx/pptx/xls 各一个试转**，
  全通才算装好。
- **旧版 .doc/.ppt 是另一回事**：markitdown 根本没有这两个格式的转换器，装依赖
  没用。解决链路在 `src/knowatlas/fetchers/office_legacy.py`：优先 LibreOffice
  （soffice headless 转换，路径可用环境变量 `KNOWATLAS_SOFFICE_PATH` 指定），
  其次 Windows COM（需要 pywin32 + 本机装有 MS Office），都没有则报错并给出
  可操作指引。**迁移到没有 Office 的机器时：装 LibreOffice，否则 .doc/.ppt 全部
  unparseable（文件是好的）。**

### 2. 本项目 venv 是 uv 管的，没有 pip

- `.venv` 由 uv 创建（Python 3.13），`python -m pip` 不存在。
- 装依赖：`uv pip install -p .venv <包名>`；日常运行：`.venv/Scripts/python.exe -m knowatlas ...`
  或 `uv run`。
- 依赖唯一权威来源是 pyproject.toml `[project].dependencies`；requirements-*.txt
  保留给 pip 用户，**改依赖两处同步**（历史教训：只改 requirements 导致
  `uv run` 报 ModuleNotFoundError: fastapi）。

### 3. 测试依赖也要装：pytest 在 pyproject `[project.optional-dependencies].dev`

## 二、Windows 环境坑

1. **CRLF**：Windows 上 Python `write_text()` 默认产 CRLF。落盘文本一律
   `newline="\n"`，收尾用字节扫描 `b"\r\n"` 确认（`grep -c $'\r'` 在 Git Bash
   下计数不可信）。
2. **fnmatch 跨分隔符失效**：Windows 上 `fnmatch.fnmatch` 先 normcase 把 `/`
   换成 `\`，跨分隔符通配直接失效。本项目已用自实现的
   `adapters/base.match_path_pattern`（逐段 + fnmatchcase），**不要改回 stdlib**。
3. **环境变量两级注册表**：查 Windows 环境变量必须同时查 HKLM（系统级）与
   HKCU（用户级），同名时**用户级优先**；setx 空值会静默成功（要回读校验）；
   已开进程读到的是启动时快照，改注册表不影响已开窗口/进程。
4. **Bash 工具偶发重复执行**：长命令/heredoc 有小概率跑两遍（第二次报
   nothing to commit 之类）。写文件、git 提交、git 推送**拆成独立命令**更稳。
5. **端口占用**：起服务前 `netstat -ano | grep LISTEN`；同端口两行 LISTEN 先
   taskkill 旧 PID。后台托管的 serve 跑完要停，别长期占用户端口（用户自己在
   终端起服务会撞 10048）。
6. **Git Bash 的 /tmp**：不直接传原生 Python，先 `cygpath -w`；路径写 `C:/...`
   原生形式，`/C:/...` 找不到。
7. **命令找不到**：Bash 报 command not found 先加
   `export PATH="/usr/bin:$PATH"`。

## 三、网络/代理坑

1. **本机全局 http_proxy 会被 httpx/urllib 自动读走**：访问 localhost/内网必须
   绕过（测试侧 conftest 已强制 `NO_PROXY=127.0.0.1,localhost`；手写脚本用
   `ProxyHandler({})`）。**本地测试假挂，第一怀疑代理**——本项目两次同源踩坑。
2. **推 GitHub 走代理**：`git -c http.proxy=http://172.16.20.27:12603 push`。
3. **reg.exe 被安全策略拦**：shell 里验证新环境变量用 Python winreg 读注册表
   注入，别调 reg.exe。

## 四、SQLite/并发坑

1. **FastAPI 线程池 + sqlite3**：主线程连接跨线程使用要 `check_same_thread=False`
   + 实例级锁串行化（DataLayer 已做，transaction 自持锁）。
2. **用户会在 Web UI 并行清理**：跑长批任务前必须重新查库快照（候选数、active
   数），别拿会话开头的数字做决策。
3. **WAL + busy_timeout** 已在连接纪律里；库被 serve 占用时 mv/删除会失败——
   用在线操作（如 `ksync --reclassify`）替代重建。

## 五、LLM/密钥坑

1. **密钥只进环境变量**（KNOWATLAS_LLM_API_KEY*、KNOWATLAS_BILI_SESSDATA 等），
   config 只写变量名，禁硬编码/入仓库/入日志。
2. **多后端/多 key 池**：`[[llm.backends]]` 数组表，书写顺序即优先级；api_key_env
   逗号分隔多变量名、变量值逗号分隔多 key，401/403/402/429 自动切换。
3. **max_batch 只认 [llm] 扁平键**，写进 [[llm.backends]] 块会被静默忽略。
4. **换 key/换变量后必须重开终端 + 重启 serve**（进程启动时读一次环境）。
5. WorkBuddy 云服务 LLM 是 MCP 工具形态，非 OpenAI 兼容端点，接不进 [llm]。

## 六、解析器/数据形态坑

1. **真实样本先行**：合成 fixture 靠想象写格式会被真实样本推翻（emmx 案例通报：
   假设的 content.xml topic 树与真实的 MindMaster 9.x Shape 结构完全不同）。
   新适配器先拿真实样本解剖定稿，再写 fixture。
2. **机器生成的大文件**：代码仓库的报表数据导出（如 rpt_maker 的 .xls，单个
   解析抽出 500 万字符、耗时 60 秒）——这类文件能解析但不该进知识库。用
   `[sources.folders].exclude_dirs` 源头剪枝（现值 vendor/samples/_legacy/.git/
   node_modules/shoes_rpt），别靠后置清理。
3. **真坏件存在**：个别 xlsx 内部 XML 损坏，Excel 能修复打开但解析器读不了
   （如 百卓/PECOS/总务料品.xlsx）——这类留在待清理候选是正确行为。
4. **解析成功 ≠ 有知识**：不可达/乱码/不具体 = 没有知识（用户铁律），抓取失败
   打标进待清理候选，由用户复核。

## 七、开发纪律坑

1. **upsert meta 合并语义是 `{**旧, **新}`**：库中已有键源不设置就保留。想删键
   必须显式 `dl.merge_meta(id, {"键": None})`（None=删键语义）——否则"补抓成功
   后旧失败打标赖着不走"这类 bug 会出现。
2. **测试写条目的硬约束**：id 必须用 `ids.entry_id()` 生成（16 位十六进制校验）、
   `exported_at` 非空、config 用 `Config` 对象（支持点路径 get，裸 dict 不行）。
3. **替换脚本的 old 字符串必须从文件原文复制**，不凭记忆重打（引号风格差异会
   导致匹配失败）。
4. **grep 模式以 `-` 开头时要写 `grep -c -e "$p"`**（会被当成选项）。
5. **Python 替换脚本注意引号风格**：原文用直角引号「」时脚本里别写成弯引号。
6. **sandbox 安全删除对 rm fail-closed**：删除用回收站/mv 改名替代。
7. **前端对新增响应字段一律 fail-open**（旧 serve 进程不重启会缺新字段，
   `!n.count` 会把"缺字段"误判成"空"）。
